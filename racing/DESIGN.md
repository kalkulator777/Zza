# Контракт проекта: браузерные 3D-гонки для локальной сети

Это **обязательный контракт**. Все модули пишутся разными исполнителями параллельно,
поэтому имена файлов, экспортируемые функции, формат данных и порядок операций
в физике зафиксированы здесь и не подлежат изменению в одностороннем порядке.
Если контракт где-то противоречив или недостаточен — не додумывай молча,
сообщи об этом в отчёте.

---

## 1. Целевое окружение и бюджет

| Параметр | Значение |
|---|---|
| Машины | Linux, Intel N5105 (Jasper Lake, UHD Graphics 24 EU) |
| Доступно | Python 3.11, Tornado, Firefox 143. **Ничего больше ставить нельзя** |
| Сеть | локальная, RTT < 1 мс |
| Игроков в гонке | до 8 |
| Интернета на машинах нет | все зависимости лежат в репозитории |

### Бюджет производительности (это требование, а не пожелание)

Клиент, разрешение 1280x720, восемь машин на экране:

- **не ниже 60 fps** на высоком пресете — пересмотрено после плейтеста
  на целевом железе, где игра выдала 100 fps. Низкий пресет обязан
  оставаться быстрым: это запас для машин слабее целевой
- **около 50 draw call** на кадр — фактический максимум после доработки
  графики (было 60 как потолок)
- **около 150 000 треугольников** в кадре
- **ноль аллокаций в кадровом цикле** — все векторы, матрицы и частицы
  выделяются заранее и переиспользуются. Никаких `new THREE.Vector3()`,
  литералов массивов, `.map`, `.filter`, замыканий внутри кадрового цикла
- **никаких shadow map**, никакой постобработки, никакого MSAA
- пиксель-рейт ограничен: `min(devicePixelRatio, 1)`, плюс настраиваемый
  render scale 50/75/100 %

Сервер:

- тик 60 Гц, **не более 2 мс на тик** при восьми машинах
- ноль блокирующих вызовов в IOLoop

Любой модуль обязан укладываться в свою долю бюджета. Оптимизация — не
финальная полировка, а условие приёмки.

## 2. Как это запускается

Один процесс `run.py` делает всё сразу:

```
python3 run.py                 # сервер + открывает Firefox на localhost
python3 run.py --no-browser    # только сервер (headless)
python3 run.py --port 8000
python3 run.py --name "Комп Васи"
```

- HTTP + WebSocket: один порт (по умолчанию 8000)
- UDP-маяк для обнаружения других серверов в сети: порт 8001
- Кто запустил `.py`, тот получает URL с токеном хоста:
  `http://localhost:8000/?host=<token>`. Токен отмечает хозяина сервера
  (`welcome.is_host`) и больше ничего не разрешает
- **Комнату создаёт любой подключившийся.** Первоначальное ограничение
  «только хозяин» держалось на недоразумении и снято вместе с ключом
  `--guest-rooms`
- Все остальные заходят браузером на `http://<ip-хоста>:8000` и получают
  ровно тот же функционал
- Клиент может увидеть другие серверы в сети (список приходит с сервера,
  который собрал его по UDP) и перейти на них по ссылке

## 4. Система координат

Правая система, **Y — вверх**, земля — плоскость XZ. Полностью совместима с three.js.

- `yaw` — поворот вокруг Y, в радианах, ноль означает «нос машины смотрит в +Z»
- `forward = ( sin(yaw), cos(yaw) )` в координатах (x, z)
- `lateral = ( cos(yaw), -sin(yaw) )` в координатах (x, z)

**Про имя `lateral`.** В первой редакции этот вектор назывался `right`, и это
было ошибкой. Камера позади машины смотрит вдоль +Z, а её экранное «вправо»
в three.js — это мировое −X. Значит, вектор `(cos yaw, -sin yaw)`, равный +X
при `yaw = 0`, указывает на экранно ЛЕВУЮ сторону машины. Математика верна и
симметрична, неверным было только название. Поэтому: вектор зовётся `lateral`,
его положительное направление — левый борт машины, положительный `steer` —
поворот налево, положительная нормаль трассы `nx, nz` смотрит туда же.
- Это ровно то, что делает `object.rotation.y = yaw` в three.js для модели,
  построенной носом в +Z
- Клавиша «влево» увеличивает yaw, «вправо» — уменьшает

**Высота (y) на физику не влияет — с одной оговоркой (см. 12.18).** Положение
на трассе строго двумерное (x, z): прогресс, отсечки, границы полотна и
столкновения машин высоты не знают. Профиль высот самой трассы остаётся
косметикой — он берётся из геометрии и применяется к визуалу: позиция машины
по Y, наклон кузова (pitch) по уклону, положение камеры. Это осознанное
упрощение: оно даёт рельеф бесплатно и убирает целый класс расхождений между
Python и JS.

Оговорка: у машины есть **одна** вертикальная степень свободы под баллистику
прыжка с трамплина — поля `height` и `v_vert` (6.1, шаг 14б в 6.2). Высота
меряется **от полотна**, а не от мира, поэтому косметичность профиля трассы
и закрытый класс расхождений сохраняются: прыжок считается одинаково
независимо от того, на подъёме трамплин или на спуске.

Единицы: метры, секунды, радианы. Скорость в м/с (в HUD переводится в км/ч).

## 5. Сетевой протокол

Транспорт — один WebSocket на `/ws`. Текстовые кадры — JSON для событий,
бинарные — для потока состояния. Различаются по типу кадра: в Tornado
`on_message` получает `str` для текста и `bytes` для бинарных данных.

### 5.1. Частоты

| Поток | Частота |
|---|---|
| Шаг симуляции (сервер и предсказание на клиенте) | 60 Гц, фиксированный шаг `dt = 1/60` |
| Ввод: клиент -> сервер | 60 Гц (каждый шаг) |
| Снапшот: сервер -> клиент | 20 Гц (каждый третий тик) |
| JSON-события | по факту |

### 5.2. Бинарный ввод: клиент -> сервер

Little-endian. Тип `0x01`.

```
u8   type = 0x01
u32  seq          порядковый номер шага клиента, монотонно растёт
u8   buttons      битовая маска
u8   reserved = 0
```

Маска `buttons`:

| бит | значение |
|---|---|
| 0 | газ |
| 1 | тормоз / задний ход |
| 2 | влево |
| 3 | вправо |
| 4 | дрифт (ручник) |
| 5 | применить бонус |
| 6 | взгляд назад |
| 7 | резерв |

Итого 7 байт на пакет.

### 5.3. Бинарный снапшот: сервер -> клиент

Тип `0x10`. Little-endian.

```
u8   type = 0x10
u32  tick            номер тика сервера
u32  ack_seq         последний seq ЭТОГО клиента, учтённый сервером
u8   car_count     биты 0..3 — число машин 0..8; бит 7 — SNAPSHOT_FLAG_EXTRA
  на каждую машину:
  u8   slot          0..7
  u8   flags         см. ниже
  f32  x
  f32  z
  f32  yaw
  f32  vx
  f32  vz
  u8   lap           пройдено полных кругов
  u8   place         место в гонке, 1..8
  i8   steer_q       угол руля, -127..127 -> -1..1 (для визуала колёс)
  u8   drift_charge  0..255 (для визуала искр)
  u8   height_q      высота над полотном в сантиметрах, 0..2,55 м (12.18)
u8   proj_count
  на каждый снаряд:
  u16  id
  u8   kind          см. таблицу бонусов
  f32  x
  f32  z
  f32  yaw
u8   box_mask_len
  box_mask_len байт   битовая маска активных боксов с бонусами

  ТОЛЬКО при поднятом бите 7 в car_count (SNAPSHOT_FLAG_EXTRA), см. 12.20:
  u8   traffic_count
    на каждую болванку 6 байт: u8 ident, u16 s_q, i8 lat_q, i8 dyaw_q, u8 spd_q
  u8   event_count
    на каждое происшествие 8 байт: id, kind, phase, s_q, lat_q, hl_q, hw_q
```

Запись машины — **27 байт**. Бит 7 не поднят: пакет ровно прежний, байт в
байт, без обеих хвостовых секций.

Флаги машины:

| бит | значение |
|---|---|
| 0 | вне трассы |
| 1 | дрифтует |
| 2 | ускорение активно |
| 3 | крутит (получил урон) |
| 4 | под щитом |
| 5 | финишировал |
| 6 | отключился, машина-призрак |
| 7 | тормозит (для стоп-сигналов) |

Размер: заголовок 10 байт + 26 на машину + 1 + 15 на снаряд + 1 + маска.
Восемь машин, четыре снаряда, маска в 2 байта: 10 + 208 + 1 + 60 + 1 + 2 = **282 байта**.
На 20 Гц это 5,5 КБ/с на клиента.

Список полей выше первичен. Если он разойдётся с подсчётом размера — прав список.

## 6. Физика

Физика **зеркалируется** в `game/physics.py` и `static/js/physics.js`.
Обе реализации обязаны выполнять операции в одном и том же порядке, с одними
и теми же константами. И Python, и JavaScript считают в float64, поэтому при
совпадающем порядке операций результаты сходятся до последнего бита, кроме
`sin` и `cos` — там допустимо расхождение в младшем разряде, его гасит
реконсиляция.

**Запрещено** использовать `exp`, `pow`, `atan2` в шаге физики: все
коэффициенты затухания заданы сразу «на шаг» при фиксированном `dt = 1/60`.

### 6.1. Состояние машины

```
x, z          позиция, м
yaw           курс, рад
vx, vz        скорость в мировых координатах, м/с
steer         текущий угол руля, -1..1
drift_charge  накопленный заряд заноса, с
drift_dir     сторона заноса: +1 несёт влево, -1 вправо, 0 стороны нет
              (в снапшот не едет, но кольцо предсказания обязано его хранить)
drift_active  идёт ли занос
boost_time    остаток ускорения, с
spin_time     остаток раскрутки после урона, с
shield_time   остаток щита, с
slow_time     остаток замедления, с
progress      накопленный путь по трассе, м (может превышать длину круга)
sample_idx    индекс ближайшей точки осевой линии, для быстрого поиска
```

### 6.2. Порядок операций в шаге

Ровно этот порядок, ровно эти шаги:

```
1.  Если spin_time > 0: ввод руля и газа игнорируется,
    yaw += SPIN_RATE * dt, spin_time -= dt
2.  Целевой угол руля: steer_target = (влево ? +1 : 0) + (вправо ? -1 : 0)
3.  steer приближается к steer_target со скоростью STEER_RATE * dt,
    при отсутствии ввода возвращается к нулю со скоростью STEER_RETURN * dt,
    результат ограничивается диапазоном [-1, 1]
4.  forward = (sin yaw, cos yaw), right = (cos yaw, -sin yaw)
5.  v_fwd = vx*forward.x + vz*forward.z
    v_lat = vx*right.x   + vz*right.z
6.  Продольная сила:
      газ    -> a = engine_force * (1 - v_fwd / max_speed_eff), не меньше нуля
      тормоз -> если v_fwd > 0.5: a = -brake_force
                иначе             a = -reverse_force
      иначе  -> a = 0
    v_fwd += a * dt
    если нажат ручник: v_fwd уменьшается на HANDBRAKE_DECEL * dt,
                       не переворачивая знак
7.  Ускорение от бонуса: если boost_time > 0, v_fwd подтягивается к
    boost_speed со скоростью BOOST_ACCEL * dt, boost_time -= dt
8.  Замедление от бонуса: если slow_time > 0, v_fwd *= SLOW_FACTOR,
    slow_time -= dt
9.  Поворот, ограниченный сцеплением:
      speed_factor = min(|v_fwd| / TURN_FULL_SPEED, 1)
      falloff      = 1 - TURN_FALLOFF * clamp((|v_fwd| - TURN_FULL_SPEED) /
                         (max_speed - TURN_FULL_SPEED), 0, 1)
      rate = steer * turn_rate * speed_factor * falloff * sign(v_fwd)
      если занос: rate *= HANDBRAKE_TURN_GAIN
      lat_limit = grip_step * GRIP_LAT_ACCEL           # м/с²
      если занос: lat_limit *= HANDBRAKE_LAT_GAIN
      rate ограничивается по модулю величиной
                  lat_limit / max(|v_fwd|, LAT_CAP_MIN_SPEED)
      yaw += rate * dt

    **Предел по сцеплению — правка контракта, внесённая по итогам плейтеста.**
    Без него скорость в дуге радиуса R равна `R * turn_rate * falloff`, то есть
    от сцепления не зависит вообще, и характеристика `grip_step` была
    декорацией: заказчик справедливо заметил, что машины не различаются.
    Теперь скорость в дуге равна `sqrt(a_lat * R)`, и сцепление даёт реальную
    разницу около 12 % скорости в повороте.

    Честное следствие: при жёстком пределе `turn_rate` перестаёт определять
    время круга — выше примерно 7 м/с всегда упирается предел сцепления.
    Поэтому `turn_rate` теперь отвечает за остроту руля (сколько лока нужно
    докрутить до предельного поворота) и за развороты на малой скорости.
10. Боковое сцепление:
      g = drift_active ? drift_grip_step : grip_step
      v_lat *= (1 - g)
11. Сопротивление:
      v_fwd -= (drag * v_fwd * |v_fwd| + roll * v_fwd) * dt
    вне трассы дополнительно: v_fwd *= OFFTRACK_FACTOR
12. Сборка скорости обратно:
      vx = forward.x * v_fwd + right.x * v_lat
      vz = forward.z * v_fwd + right.z * v_lat
13. Интегрирование: x += vx * dt, z += vz * dt
14. Границы трассы: запрос к track, выталкивание внутрь, гашение
    нормальной составляющей скорости с коэффициентом WALL_BOUNCE
15. Заряд дрифта: см. 6.3
16. Обновление progress и sample_idx через track
```

Форма столкновения — **капсула 4,00 x 1,90 м**: продольный отрезок длиной
`2 * CAR_AXIS_HALF`, обмотанный радиусом `CAR_RADIUS`. Расстояние меряется
между отрезками двух машин. Прежний круг диаметром 2,2 м при длине кузова
4 м давал сквозной проезд почти на два метра до срабатывания и при этом
цеплял соседа на параллельной прямой.

Столкновения машина-машина считает **только сервер**, отдельной функцией
`resolve_collisions`, **после того как шаг сделали все машины**. Клиент их
не предсказывает.

Первоначальная формулировка «между шагами 14 и 15» была невыполнима: чтобы
влезть внутрь шага, его пришлось бы резать надвое и тащить локальные величины
через поля состояния. Разница в поведении ровно одна — `progress` толкнутой
машины учитывает выталкивание на кадр позже.

### 6.3. Дрифт и награда за занос

```
Занос начинается: нажат ручник И v_fwd > HANDBRAKE_MIN_SPEED
Пока занос активен, машину реально несёт (|v_lat| > HANDBRAKE_CHARGE_SLIP * v_fwd)
и машина НЕ вне трассы:
    k = clamp((v_fwd - HANDBRAKE_MIN_SPEED) /
              (HANDBRAKE_CHARGE_FULL_SPEED - HANDBRAKE_MIN_SPEED), 0, 1)
    drift_charge += k * k * dt
Сторона заноса запоминается в drift_dir; смена стороны ОБНУЛЯЕТ drift_charge.
Пока |v_lat| внутри зоны нечувствительности HANDBRAKE_FLIP_SLIP, сторона
не меняется вовсе — дрожание руля честный занос не роняет.
Занос заканчивается при отпускании ручника или потере скорости
При завершении:
  drift_charge >= 2.4 -> ускорение 1.8 с (уровень 3, фиолетовые искры)
  drift_charge >= 1.4 -> ускорение 1.2 с (уровень 2, оранжевые искры)
  drift_charge >= 0.7 -> ускорение 0.7 с (уровень 1, синие искры)
  иначе               -> ничего
drift_charge обнуляется
```

Поле `drift_charge` в снапшоте передаётся как `min(255, round(charge * 100))`,
рендер по нему рисует искры нужного цвета.

скорости: угол скольжения разносило до 50–57°, продольная скорость падала

уровни 2 и 3 были недостижимы в принципе. Поэтому шаг 10 дополнительно
ограничивает угол скольжения потолком `DRIFT_MAX_SLIP`, а срезанную часть
заноса не выбрасывает, а возвращает в продольную скорость с коэффициентом
`DRIFT_SLIDE_RECOVER`. Замер после правки: полный руль на сцеплении даёт
поворот 81° за 0,75 с, по ручнику — 124°, ловится за 0,20 с.

## 7. Трассы

### 7.1. Описание трассы: `content/tracks/<id>.json`

Это **исходное** описание, которое пишет человек. Производная геометрия
считается на сервере и рассылается клиентам.

```json
{
  "id": "office",
  "name": "Офисный круг",
  "desc": "Широкая, прощает ошибки",
  "difficulty": 1,
  "theme": "city",
  "width": 14.0,
  "control": [ [x, z], [x, z], ... ],
  "width_overrides": [ {"at": 0.42, "width": 10.0, "blend": 0.05 } ],
  "elevation": [ {"harmonic": 1, "amp": 4.0, "phase": 0.0 },
                 {"harmonic": 3, "amp": 1.5, "phase": 1.1 } ],
  "item_rows": [ {"at": 0.18, "count": 5}, {"at": 0.55, "count": 3} ],
  "decor_seed": 12345,
  "start_offset": 0.0,
  "time_of_day": "day"
}
```

- `control` — контрольные точки замкнутого сплайна Catmull-Rom (центростремительный,
  alpha = 0.5), последняя точка соединяется с первой
- `width` — половина ширины полотна в метрах умножается на 2; то есть это
  полная ширина. `width_overrides` сужают или расширяют трассу на доле `at`
  от длины круга, с плавным переходом длиной `blend`
- `elevation` — высота задаётся **только периодическими гармониками** от
  нормированной длины дуги: `y(s) = Σ amp_i * sin(2π * harmonic_i * s / L + phase_i)`.
  Это гарантирует, что круг сходится по высоте без швов
- `item_rows` — ряды боксов с бонусами поперёк трассы
- `decor_seed` — зерно детерминированного генератора окружения; и сервер,
  и клиент обязаны получить одинаковый декор

Три трассы:

| id | Название | Характер |
|---|---|---|
| `office` | Офисный круг | широкая, плавная, для новичков, городская тема |
| `serpentine` | Серпантин | узкая, сильный рельеф, шпильки, горная тема |
| `industrial` | Промзона | техничная, шикана, перепады ширины, индустриальная тема |

### 7.2. Производная геометрия

`game/track.py` строит из описания:


### 7.3. Публичный интерфейс `game/track.py`

```python
class Track:
    @classmethod
    def load(cls, path: str) -> "Track": ...

    length: float
    samples: list          # структура из 7.2
    item_boxes: list
    start_grid: list

    def nearest_index(self, x: float, z: float, hint: int) -> int:
        """Локальный поиск ближайшей точки осевой линии вокруг hint."""

    def surface(self, x: float, z: float, hint: int) -> tuple:
        """(index, lateral, half_width, y, pitch)
        lateral — знаковое смещение от оси, положительное влево (см. раздел 4)."""

    def clamp_to_track(self, state, hint: int) -> None:
        """Шаг 14 физики: выталкивание из стены, гашение скорости."""

    def advance_progress(self, state, hint: int) -> None:
        """Шаг 16 физики: обновление progress с корректной обработкой
        перехода через линию старта и защитой от срезок."""

        """Сериализация в JSON для клиента, поле track в race_init."""
```

`static/js/track.js` экспортирует **тот же набор** в виде класса `Track`
с методами `nearestIndex`, `surface`, `clampToTrack`, `advanceProgress`,
и конструктором `Track.fromServer(data)`, принимающим объект из `race_init`.
Логика обязана совпадать с Python построчно.

### 7.4. Прогресс, круги и защита от срезок

- `progress` — накопленный путь по дуге, в метрах, растёт монотонно
- На каждом шаге: `s_new` из ближайшей точки, `ds` — кратчайшая разница с
  учётом замыкания круга. Если `|ds| > length / 4`, шаг игнорируется
  (телепорт или шум)
- `progress += ds`
- `lap = floor(progress / length)`
- Дополнительно машина обязана последовательно пройти все 12 отсечек за круг;
  пропуск отсечки не засчитывает круг. Это ловит срезание по траве
- Место в гонке = сортировка по `progress` убыванием, финишировавшие всегда выше

## 9. Комнаты и состояния

### Состояния комнаты

```
LOBBY -> COUNTDOWN -> RACING -> RESULTS -> LOBBY
```

- `LOBBY` — игроки выбирают машину и цвет, жмут «готов». Владелец комнаты
  меняет настройки и запускает гонку
- `COUNTDOWN` — 3 секунды, машины на решётке, ввод заблокирован
- `RACING` — гонка. Финишировавшие переходят в режим наблюдателя,
  их машина остаётся на трассе как призрак и удаляется через 3 с
- `RESULTS` — 15 секунд таблица, затем автоматически обратно в LOBBY
- Вошедший во время `RACING` ждёт в наблюдателях до следующей гонки
- Если гонка не закончена за `RACE_TIMEOUT = 10` минут — принудительные итоги
- После финиша лидера остальным даётся `FINISH_GRACE = 45` с

### Настройки комнаты (задаются при создании, меняются владельцем в лобби)

```json
{
  "track": "office",
  "time_of_day": "day",
  "weather": "clear",
  "traffic": "off",
  "events": "off",
  "laps": 3,
  "max_players": 8,
  "items_enabled": true,
  "items": ["boost", "rocket", "mine", "shield", "storm"],
  "collisions": true,
  "mirror": false
}
```

`laps` — от 1 до 9. `mirror` — зеркальная трасса, дешёвое разнообразие.

`time_of_day` — `day | dusk | night`. Умолчание берётся из описания выбранной
трассы. **Правило при смене карты:** значение, равное предложению прежней карты,
следует за новой; выбранное человеком вручную сохраняется. Когда выбранное
расходится с предложением карты, интерфейс показывает подсказку
«Карта предлагает: ...» — чтобы правило не было молчаливым. Отдельного флага
«выбрано вручную» нет намеренно: он взводился бы самой формой создания,
которая всегда шлёт поле, и умолчание карты перестало бы работать.

## 10. Клиентская часть

### 10.1. Главный цикл, `js/main.js`

```
requestAnimationFrame ->
  накопитель времени
  пока accumulator >= dt:
      собрать ввод
      предсказать свою машину шагом physics.step (тот же dt)
      сохранить (seq, input, state) в кольцевой буфер на 120 записей
      отправить бинарный ввод
      accumulator -= dt
  alpha = accumulator / dt
  отрисовать кадр с интерполяцией между предпоследним и последним состоянием
```

Кадровый цикл не должен аллоцировать. Кольцевой буфер выделяется один раз
типизированными массивами.

### 10.2. Реконсиляция, `js/net.js`

При получении снапшота:

1. Взять авторитетное состояние своей машины и **`tick` снапшота**
2. Найти в кольцевом буфере собственное предсказание, помеченное тем же `tick`
3. Если расхождение позиции меньше `RECONCILE_EPS = 0.05` м — ничего не делать
4. Иначе: заменить состояние на авторитетное и **переиграть** все сохранённые
   вводы после этого момента
5. Визуальную разницу гасить плавно за `RECONCILE_SMOOTH = 0.15` с,
   чтобы коррекция не выглядела рывком

**Сверять по `ack_seq` НЕЛЬЗЯ, хотя первая редакция этого раздела так и велела.**
`ack_seq` — это номер последнего *принятого* пакета, а не «столько шагов я сделал».
Сервер тикает по своим часам независимо от приёма: если кадр клиента просел и за
один кадр ушло четыре пакета ввода, сервер примет все четыре, применит последний
и тикнет при этом **один** раз. `ack_seq` прыгнет на 4, а состояние продвинется
на 1 — и сверка сравнит разные моменты времени, выдумав расхождение на ровном
месте. Измерено: сверка по `ack_seq` давала медиану расхождения 0,34 м и 53 %
снапшотов сверх порога; сверка по `tick` — 0,0094 м и 15 %.

`tick` — это ровно «сколько шагов сделал сервер» (12.4 фиксирует
`race_time == tick_no * dt`), поэтому запись буфера с тем же индексом
и есть предсказание того же самого момента.

Чтобы индексы вообще сходились, **темп шагов клиента привязывается к тику
сервера**: `net.js` держит опережение `seq − tick` в коридоре 1..5 шагов,
отдавая поправку в накопитель главного цикла не больше трёх шагов за снапшот.
Без этого замка обе стороны считают 60 Гц по своим часам, счётчики медленно
расходятся, и реконсиляция начинает править не физику, а разницу в количестве
шагов.

**История чужих машин тоже размечается по `tick`, а не по времени прихода
пакета.** На просевшем кадре главный поток занят отрисовкой, и два снапшота,
отправленных с интервалом 50 мс, попадают в обработчик почти одновременно:
шкала времени сминается, интерполяция по смятому интервалу даёт рывок.
Местные часы привязываются к серверным минимумом разности «приход минус
серверное время» по окну в 64 замера. Измерено: разметка по времени прихода
давала 51 % кадров с отклонением скорости больше половины, разметка
по `tick` — 1,3 %.

Чужие машины: буфер снапшотов, отрисовка на момент `now - INTERP_DELAY`,
где `INTERP_DELAY = 100` мс. Интерполяция Эрмита по позиции и скорости,
углы интерполируются по кратчайшей дуге. При нехватке данных — экстраполяция
не дольше 250 мс, затем заморозка.

### 10.3. Рендер, `js/render/`

Требования, вытекающие из бюджета:

- Статика трассы — **по одному мешу на материал, нарезанному на сегменты**
  вдоль дуги: полотно, бордюры и рельеф делят материал и слиты в один меш,
  разметка во второй. Каждый рисуется 1–3 вызовами по видимым сегментам.
  Собственная функция слияния геометрий, `BufferGeometryUtils` не вендорить
- Декор (деревья, столбы, отбойники, трибуны, здания) — только `InstancedMesh`,
  по одному на тип
- Материалы: `MeshLambertMaterial` с `flatShading: true` и вершинными цветами.
  Никаких текстур-файлов; если нужна текстура — генерировать в canvas
- Свет: одна `AmbientLight` + одна `DirectionalLight`. Тени выключены
- Тень машины — тёмный круг-декаль под кузовом, полупрозрачный, без карт теней
- Небо — градиентная полусфера на вершинных цветах + `scene.fog` (linear),
  дальность тумана согласована с дальностью отрисовки
- Машина: кузов из процедурного низкополигонального профиля (капот, кабина,
  крылья, спойлер), четыре колеса с дисками, фары как эмиссивные плоскости,
  стоп-сигналы загораются по флагу торможения, голова водителя.
  **Это не коробка с колёсами** — силуэт должен читаться как машина
- Эффекты (`effects.js`): дым от дрифта, искры заряда дрифта по уровням,
  след ускорения, взрыв при попадании, вращение боксов. Всё на пулах
  инстансов с фиксированным потолком, ноль аллокаций
- Камеры: **от третьего лица** (пружинная, с зависимостью FOV от скорости
  и лёгкой тряской) и **от первого лица** из кокпита с простой панелью и рулём.
  Переключение клавишей `C`. Плюс «взгляд назад» на удержание
- Настройка качества: три пресета (низкое / среднее / высокое), а под ними
  шесть **отдельных переключателей** (затенение, свечение, анимация декора,
  плотность декора, частицы, чёткость картинки). Пресет — быстрая заготовка,
  которая выставляет все шесть скопом.
  По умолчанию — среднее. Пресет сохраняется в `localStorage`

## 12. Приложение: точные форматы обмена

Эти два формата — стык между исполнителями, поэтому заданы до поля.

### 12.1. `Track.to_client()` — объект `track` в событии `race_init`

Точки осевой линии передаются **плоскими массивами**, а не массивом объектов:
JSON получается втрое компактнее, а клиент сразу заливает их в `Float32Array`
без перебора.

```jsonc
{
  "id": "office",
  "name": "Офисный круг",
  "theme": "city",              // city | mountain | industrial
  "length": 1284.6,             // длина круга, м
  "sample_step": 2.0,
  "count": 642,                 // число точек, длина каждого массива ниже
  "x":  [...], "y":  [...], "z":  [...],   // точка осевой линии
  "tx": [...], "tz": [...],                // единичная касательная
  "nx": [...], "nz": [...],                // единичная нормаль, направлена влево (раздел 4)
  "hw": [...],                             // половина ширины полотна в этой точке
  "s":  [...],                             // расстояние по дуге от старта
  "checkpoints": [0, 53, 107, ...],        // 12 индексов
  "item_boxes": [{"id": 0, "x": 1.2, "z": 3.4, "s": 220.0}],
  "start_grid": [{"x": 0.0, "z": -6.0, "yaw": 0.0}],   // 8 мест
  "decor_seed": 12345,
  "time_of_day": "night"      // умолчание карты, не выбор комнаты
}
```

Замыкание круга: точка с индексом `count - 1` соседствует с точкой `0`.
Массивы не дублируют первую точку в конце.

Клиент строит `Track.fromServer(data)` и хранит массивы как `Float32Array`.

### 12.2. Поле `shape` в `content/cars.json`

Модель машины строится процедурно из этих параметров. Все размеры в метрах.

```jsonc
{
  "style": "hatch",        // hatch | muscle | buggy | van | wedge
  "length": 4.10,
  "width": 1.85,
  "height": 1.24,
  "wheelbase": 2.50,       // расстояние между осями
  "track_width": 1.62,     // расстояние между колёсами поперёк
  "wheel_radius": 0.34,
  "wheel_width": 0.25,
  "ride_height": 0.14,     // просвет
  "cabin_start": 0.34,     // доля длины, где начинается кабина (от носа)
  "cabin_end": 0.78,       // доля длины, где кабина кончается
  "cabin_height": 0.52,    // высота кабины над кузовом
  "nose_drop": 0.16,       // насколько нос ниже кузова
  "tail_drop": 0.08,
  "taper_front": 0.82,     // сужение кузова к носу, доля ширины
  "taper_rear": 0.94,
  "spoiler": true,
  "spoiler_height": 0.34,
  "accent": "#1d1f24"      // цвет пластика, стёкол и бамперов
}
```

Пять стилей обязаны читаться с первого взгляда и по силуэту:

| style | Образ |
|---|---|
| `hatch` | компактный трёхдверный хэтчбек, сбалансированный |
| `muscle` | длинный низкий капот, широкая корма, тяжёлый |
| `buggy` | багги с открытым верхом, большие колёса, каркас, юркий |
| `van` | высокий фургон, тяжёлый, устойчивый в столкновениях |
| `wedge` | клин, очень низкий, быстрый, плохо поворачивает |

Основной цвет кузова задаёт игрок, `accent` — из описания машины.

### 12.3. Протокол: детали, зафиксированные при реализации

Эти решения не были описаны изначально. Теперь они часть контракта, потому
что на них завязаны `sim.py`, `net.js` и рендер.

**Формат входных данных при сборке снапшота.** Никаких словарей и объектов в
горячем пути — только кортежи строго в порядке полей:

```python
car  = (slot, flags, x, z, yaw, vx, vz, lap, place, steer_q, drift_charge)
proj = (id, kind, x, z, yaw)
```

**Переиспользование снапшота между клиентами.** Общая часть собирается один
раз за тик, на клиента подменяются только четыре байта `ack_seq`:

```python
buf = protocol.build_snapshot_base(tick, cars, projectiles, box_mask)
for player in room.players:
    protocol.stamp_ack(buf, player.ack_seq)
    player.ws.write_message(buf, binary=True)
```

`encode_snapshot(...)` остаётся как обёртка для одиночных отправок и тестов.
Измерено: рассылка на восемь клиентов — 3,9 мкс за тик против 21,3 мкс при
наивной пересборке.

**Порядок бит в маске боксов.** Бокс `i` лежит в байте `i >> 3`, бит `i & 7`,
младший бит первый.

**Квантование угла руля.** `steer_q = round(steer * 127)` с округлением от нуля
и клампом в `[-127, 127]`. Клиент деквантует сразу при разборе, поэтому в
клиентском буфере поле `carSteer` — уже `Float32` в диапазоне `[-1, 1]`.

**Переполнение.** `MAX_CARS = 8`, `MAX_PROJECTILES = 32`, `MAX_BOX_MASK_LEN = 32`
(то есть до 256 боксов). Сервер молча обрезает лишнее, клиент отвергает
снапшот с превышением. Ронять тик или соединение из-за этого нельзя.
Константы экспортируются из обоих модулей, `items.py` обязан на них смотреть.

**Клиентский буфер снапшота.** `createSnapshotBuffer()` возвращает объект с
типизированными массивами фиксированного размера. Имена полей — часть
контракта, `net.js` и рендер читают именно их:

```
tick, ackSeq, valid
carCount, carSlot, carFlags, carX, carZ, carYaw, carVx, carVz,
carLap, carPlace, carSteer, carDriftCharge, indexBySlot
projCount, projId, projKind, projX, projZ, projYaw
boxMaskLen, boxMask
```

`indexBySlot[slot]` даёт индекс машины в массивах или `-1`, если машины нет.
`decodeSnapshot(data, out)` возвращает `true` или `false` и при `false`
не портит ранее разобранные данные.

**Про нулевые аллокации на клиенте.** Полностью нуля достичь нельзя: каждое
сообщение WebSocket приходит новым `ArrayBuffer`, поэтому один `DataView`
на снапшот неизбежен. Он создаётся 20 раз в секунду вне кадрового цикла и
кэшируется. Кадровый цикл читает только из типизированных массивов и не
аллоцирует ничего.

### 12.4. Стык сервера и симуляции

Сервер ничего не знает про физику, бонусы и трассу: он только крутит тик,
раздаёт снапшоты и рассылает события. Вся игровая логика живёт за этим
интерфейсом.

```python
class Simulation:
    """Одна гонка в одной комнате. Живёт от старта до итогов."""

    def __init__(self, track, settings, players): ...
        # players: [{"slot", "name", "car_id", "color"}], расстановка по start_grid

    tick_no: int          # номер тика, растёт с нуля

    def set_input(self, slot: int, seq: int, buttons: int) -> None:
        """Принять ввод от игрока. Пакеты приходят не по порядку и дублируются:
        устаревший seq игнорируется молча."""

    def tick(self) -> list:
        """Один шаг 1/60 с. Возвращает список событий race_event (уже готовые
        словари по схеме раздела 9) — сервер просто рассылает их как есть."""

    def snapshot_args(self) -> tuple:
        """(cars, projectiles, box_mask) в формате раздела 12.3,
        готовые к передаче в protocol.build_snapshot_base."""

    def ack_seq(self, slot: int) -> int:
        """Последний учтённый seq этого игрока — для stamp_ack."""

    def is_over(self) -> bool: ...
    def results(self) -> list:
        """rows для события results по схеме раздела 9."""

    def drop_player(self, slot: int) -> None:
        """Игрок отключился: машина становится призраком и через 3 с исчезает."""
```

Сервер обязан вызывать `tick()` с фиксированным шагом 1/60 с, компенсируя
дрейф таймера накопителем, и отправлять снапшот каждый третий тик.
Если процесс отстал больше чем на 10 тиков — пропустить отставание,
а не пытаться нагнать: лучше рывок, чем спираль смерти.

### 12.5. Физика: детали, зафиксированные при реализации

**`max_speed` — это НЕ фактическая максимальная скорость,** а опорная скорость
двигателя. Тяга падает как `engine_force * (1 - v / max_speed)`, поэтому
реальный потолок берётся из равновесия тяги и сопротивления:

```
engine_force * (1 - v / max_speed) = drag * v² + roll * v
```

Характеристики в `content/cars.json` обязаны подбираться по решению этого
уравнения и проверяться замером, а не по значению поля `max_speed`.
Для аркадного ощущения `roll` держим в пределах 0,02…0,06, `drag` — 0,0003…0,0008,
чтобы основным ограничителем работал член `(1 - v / max_speed)`, а не трение.

**`max_speed_eff` в шаге 6** — это `boost_speed`, пока `boost_time > 0`,
иначе `max_speed`.

**Задний ход ограничен** `REVERSE_MAX_SPEED` по той же формуле, что и газ.
Без ограничения машина разгонялась назад до 26 м/с.

**`shield_time` убывает в шаге 1** вместе с остальными таймерами — в исходном
порядке операций он не убывал вообще.

**Поле `offtrack`** добавлено в состояние: его пишет `clamp_to_track` (шаг 14),
а читает шаг 11, используя значение с прошлого шага. Оно же едет в снапшот
как бит 0 флагов.

**`CarState` объявлен с `__slots__`** ради скорости, поэтому завести на нём
произвольное поле извне НЕЛЬЗЯ. Доступный набор полей — ровно из раздела 6.1
плюс `lap`, `checkpoint`, `offtrack` для нужд `track.py` и `drift_dir`. Если модулю трассы
понадобится больше — это правка контракта, а не молчаливое добавление.

**`car_stats` — объект с атрибутами, а не словарь.** Шаг читает атрибуты:
это заметно дешевле в горячем пути. `game/cars.py` может отдавать что угодно
с нужными атрибутами, `CarStats.from_dict` — готовый вариант.

**Имена полей состояния на JS — camelCase:** `driftCharge`, `boostTime`,
`sampleIdx`, `spinTime`, `shieldTime`, `slowTime`, `offtrack`. Это стык
с `track.js` и `net.js`, расхождение в именах разваливает предсказание молча.

### 12.6. Решения по итогам второй волны

Сведено из отчётов исполнителей сервера, мешей и интерфейса. Всё ниже —
часть контракта.

**Tornado не принимает `bytearray`.** `write_message` прогоняет payload через
`tornado.escape.utf8`, который бросает `TypeError` на всём, кроме `bytes`
и `str`. Проверено. Поэтому пример в 12.3 читается так:

```python
buf = protocol.build_snapshot_base(tick, cars, projectiles, box_mask)
for player in room.players:
    protocol.stamp_ack(buf, player.ack_seq)
    player.ws.write_message(bytes(buf), binary=True)   # копия обязательна
```

Копия стоит около 0,1 мкс на клиента и схему base/stamp не обесценивает.
Отдельно: клиент обязан слать ввод именно бинарным кадром. Текстовый кадр
с недопустимым UTF-8 Tornado закрывает как нарушение протокола.

**Комнаты и игроки.**

- Стартовая расстановка: список `players` сортируется по слоту, индекс
  в списке равен индексу места на решётке. `race_init` объявляет ту же.
- Наблюдатель занимает слот и считается в `max_players`.
- При выходе владельца комнаты владение переходит к тому, кто вошёл раньше всех
  из оставшихся.
- Минимум для старта — один игрок: тренировка в одиночку разрешена.
- Лимиты соединения: 40 JSON-событий и 180 бинарных пакетов в секунду,
  пять секунд подряд превышения — разрыв. Чат: 160 символов, 3 сообщения
  за 2,4 с.
- Коды ошибок: `no_hello`, `already`, `bad_json`, `bad_event`, `unknown_event`,
  `no_room`, `bad_room`, `room_full`, `not_host`, `not_owner`, `busy`,
  `bad_track`, `bad_laps`, `bad_max_players`, `bad_items`, `bad_flag`,
  `bad_settings`, `bad_car`, `bad_color`, `no_cars`, `bad_ready`, `not_ready`,
  `bad_time_of_day` (и зарезервирован `bad_weather`),
  `not_enough`, `chat_rate`, `too_many_rooms`, `sim_failed`.
- Системное сообщение чата помечается `slot < 0`.
- Известная шероховатость: каждое сообщение чата рассылает всё состояние
  комнаты. Для восьмерых в офисе это терпимо, отдельное событие `chat` —
  кандидат на потом.

**Правки схем событий.**

- В `welcome` добавляется поле `slot` — собственный слот игрока. Без него
  клиент не знает, какая строка в `players` его, владелец ли он и какой цвет
  занят им самим. `slot_token` остаётся личным токеном соединения.
- В `welcome.content.cars[]` добавляется `style` — один из
  `hatch | muscle | buggy | van | wedge`. Силуэт нужен уже в лобби.
- Поле `preview` у трасс из схемы убирается: файлов-картинок в проекте нет,
  силуэт рисуется инлайновым SVG по теме.
- `ping` измеряется в миллисекундах. `servers[].url` — абсолютный URL.

**Клиентский `Track` (`static/js/track.js`).** Плоские массивы из 12.1 живут
в полях `cx, cy, cz, ctx, ctz, cnx, cnz, chw, cs`, плюс `step`, `decorSeed`,
`length`, `count`. Это имена, на которые смотрят рендер и сетевой код.

**Рельеф и качество.** Высоты вокруг трассы нужны и мешу ленты, и расстановке
декора. Источник один: `createTerrainSampler(track, theme, quality)` из
`trackmesh.js`. `renderer.js` **обязан** вызвать `buildTrackMeshes` и
`buildScenery` с одним и тем же `quality`, иначе декор всплывёт над землёй.

**Что возвращает `buildScenery`:** `fog {color, near, far}`, `background`,
`light.ambient`, `light.directional`, `updateSky(camera)`. Рендер обязан это
применить и звать `updateSky` каждый кадр.

**Зоны ответственности, которые не были назначены.**

- Тень под машиной — на `renderer.js`: один `InstancedMesh` на все восемь
  машин, а не пятый draw call каждой.
- Меши боксов с бонусами — на `renderer.js` (один `InstancedMesh`),
  вращение и подсветка — на `effects.js`.
- Время круга, лучший круг, отставание от лидера и бонус в руках в снапшоте
  не передаются: их считает `net.js` из `race_event` и `progress`
  и отдаёт в HUD.
- Признак «едет не туда» считает `main.js` проекцией скорости на касательную.
- Клавиши `Tab` и `F3` обрабатывают модули интерфейса сами. `input.js`
  их НЕ трогает, иначе выйдет двойная привязка.

**Модель машины.** `cabin_start` и `cabin_end` отсчитываются долями длины
**от носа**. Стиль главнее чисел: если значения из `cars.json` противоречат
силуэту стиля, они зажимаются в допустимый для стиля диапазон.
`wheels[]` — четыре прокси-`Object3D` поверх одного `InstancedMesh`,
после правки поворотов рендер обязан звать `syncWheels()`. `driver` — узел-якорь
в точке головы, к нему крепится камера из кокпита.

**Материалы.** Требование «Lambert везде» смягчается: купол неба и облака —
`MeshBasicMaterial`, иначе градиент не выразить. Это два материала.

**Каталог машин (`game/cars.py`).** `CarCatalog.load(path)`, `.ids`,

в `welcome.content.cars` больше полей, чем описано в схеме, и пропускает их
как есть.

**Пресеты качества** называются `low`, `medium`, `high`.
Ключи `localStorage`: `racing.name`, `racing.quality`, `racing.volume`,
`racing.muted`.

**Экспорты модулей интерфейса:** `MenuScreen`, `LobbyScreen`, `Hud` +

**Версия three.js — r180**, как и заявлено в разделе 3. Проверено импортом:
`REVISION === '180'`.

### 12.7. Трасса и машины: решения при реализации

**Зона вылета.** Между кромкой асфальта и жёсткой стеной лежит `WALL_MARGIN = 2.5` м:
там машина едет с `OFFTRACK_FACTOR`, флаг `offtrack` поднят. `WALL_BOUNCE = 0.35` —
коэффициент отражения нормальной составляющей скорости.

**Круг засчитывается только при пересечении линии старта с `checkpoint == 0`.**
Формулировка «`lap = floor(progress / length)`» из 7.4 противоречила требованию
«пропуск отсечки не засчитывает круг»; побеждает требование. Проверено: три
честных круга дают `lap = 3`, срезка через газон круг не засчитывает, задний
ход через линию откатывает и круг, и отсечку.

**Скачок больше четверти круга** пересинхронизирует отсчёт **только назад**.
Буквальное «шаг игнорируется» без отдельного поля приводит к тому, что машина
после телепорта застревает навсегда. Текущее поведение строже к срезкам:
прыжок через газон не даёт ни метра прогресса и при этом стоит целого круга.

**Стартовая решётка** — две колонны со сдвигом: ±2,9 м от оси, сдвиг вдоль
трассы 4,5 м, 9 м между парами в колонне, места от 8 до 38 м позади линии.

**`init_state(state)` обязателен** после расстановки на решётке, иначе
`progress` и `checkpoint` стартуют с мусора. При респауне по ходу гонки
звать не нужно, `advance_progress` разберётся сам.

**`Track.load(path, mirror=False)`** — зеркальная трасса строится на загрузке.
**Корень `cars.json`** — объект `{"note": ..., "cars": [...]}`; голый список
тоже принимается.
**`sample_step`** на замкнутом круге ровно 2,0 не бывает: фактическое значение
`L / N` уезжает в поле `sample_step`, клиент берёт его оттуда.
**`preview` трассы** — нормированный контур из 64 точек `[[x, y], ...]` в 0..1,
ось `y` направлена вниз, как на экране. Это заменяет убранное в 12.6 поле-картинку.
**`to_client()` машин** дополнительно везёт `stats` и `shape`: без `stats`
клиенту нечем кормить `physics.js`, а `shape.style` нужен лобби для силуэта.

**Разброс скоростей машин — 181…197 км/ч** (переработано после плейтеста).
Прежний диапазон 138…152 был следствием того, что в шаге 9 не было предела
по сцеплению: скорость в повороте не зависела от цепкости, преимущество
в поворотах насыщалось, и `grip_step` не влиял ни на что. Предел введён
(см. 6.2, шаг 9), и характеристики заработали.

Разброс после переработки: потолок 181…197 км/ч, разгон до сотни 2,13…3,37 с
(1,58 раза), тормозной путь 26,8…41,8 м (1,56 раза), масса 0,70…1,60
(2,29 раза), сцепление даёт 12 % разницы скорости в дуге.

Фавориты по трассам (сходятся и в расчётной модели, и в прогоне ботами):
Багги берёт короткие технические `office` и `industrial`, Хэтч — `serpentine`,
длинные скоростные `avenue` и `ridge` достаются Клину и Маслкару. Разброс
среднего времени круга по всем пяти трассам — 0,22 %, то есть доминирующей
машины нет.

Честное ограничение: трассы группируются в два типа. `office`, `serpentine`
и `industrial` нагружают сцепление (плюс 10 % сцепления даёт минус 2,3 %
круга), `avenue` и `ridge` — тягу и потолок. Поэтому пять разных победителей
на пяти трассах физически не набирается, три — набираются, и это потолок
при таком наборе трасс.

Замерено: `nearest_index` 1,0–1,1 мкс с хорошей подсказкой, 7,2–8,1 мкс
при потерянной; `surface` 1,6 мкс. На тик при восьми машинах около 20 мкс.
Геометрия трассы строится 6–7 мс и кэшируется.

### 12.8. Как клиент узнаёт свой слот

Слот — это **место в конкретной комнате**, а не личность игрока: он выдаётся
при входе, меняется при переходе в другую комнату и освобождается при выходе.
Поэтому:

```
welcome      -> slot === null (почти всегда): запомнить slot_token и is_host
room (любое) -> setLocalSlot(msg.you); владелец = (msg.you === msg.owner_slot)
leave_room   -> setLocalSlot(null): цвет освобождён
```

`you` приходит в **каждом** событии `room`, поэтому ловить какое-то особенное
«первое» событие не нужно, и после перехода в другую комнату значение
обновится само.

**Завершение гонки.** Штатный путь — `sim.is_over()`. `FINISH_GRACE` (45 с
после финиша лидера) и `RACE_TIMEOUT` (10 минут) остаются страховкой.
Все три пути протестированы: комната останавливает цикл тиков, рассылает
`results` всем, переходит в `RESULTS`, затем автоматически в `LOBBY`
со снятой готовностью.

### 12.9. Звук: интерфейс модуля

Экспорты `static/js/audio.js`: класс `RaceAudio`, фабрика `createAudioState()`,
готовый синглтон `audio`. Кадровый контракт устроен как у `Hud`: состояние —
один заранее выделенный объект с типизированными массивами по слотам,
`main.js` переписывает поля и зовёт `update`.

```
audio.attachUnlockHandlers(target)   // контекст создаётся только по жесту
audio.unlock()                       // вернёт false, если WebAudio недоступен
audio.setLocalSlot(slot)
audio.startRace() / audio.stopRace()
audio.update(state, dt)              // раз в кадр
audio.raceEvent(msg)                 // готовое событие race_event из сети
audio.countdown(value)               // countdown(0) означает старт гонки
audio.collision(force, slot)
audio.setVolume(volume, muted, persist)
audio.stats()
new RaceAudio({ createContext })     // внедрение контекста для офлайн-замеров
```

**Что обязан делать `main.js`.**

- Заполнять `state.carSpeed[i]` — в снапшоте есть только `carVx`/`carVz`.
- Ставить `state.engineOn`: в отсчёте — холостые, на экране итогов — тишина.
- Звать `audio.collision(force, slot)` самостоятельно. **Столкновений нет
  в схеме `race_event`**: их считает только сервер и наружу не отдаёт,
  поэтому из потока событий звук удара запустить нечем.
- Звать `audio.countdown(0)` при переходе комнаты в `RACING`: отдельного
  события «старт» в протоколе нет.

**Владелец ключей громкости** — `saveUiSettings` в `ui/menu.js`.
`audio.setVolume` пишет туда же те же значения, дублирование безвредно.
Отдельные шины (`engine`, `fx`, `ui`) регулируются через `setBusVolume`,
но не персистятся: ключей под них в разделе 12.6 не заведено.

**Ограничение проверки.** Firefox в среде разработки отсутствует, поэтому
весь браузерный тест шёл в Chromium. Один участок кода написан специально
под Firefox: у него нет `AudioParam.cancelAndHoldAtTime`, и запасной путь
через `cancelScheduledValues` + `setValueAtTime` защищён проверкой наличия
метода, но на живом Firefox не проверялся. Это первое, что надо посмотреть
при первом запуске на целевых машинах.

### 12.10. Бонусы и симуляция: числа и решения

**Числа бонусов**, которых не было в разделе 8:

```
мина:    раскрутка 1,0 с, взводится 0,5 с, живёт 25 с
ракета:  46 м/с, поворот 2,4 рад/с, живёт 5 с, радиус поражения 2,8 м,
         раскрутка при попадании 1,5 с
подбор бокса: радиус 2,2 м, восстановление 6 с
```

- Щит гасит и грозу тоже: гроза — это попадание, значит `blocked: true`
  и щит тратится.
- Ракета у лидера цели не имеет (впереди никого): летит прямо, может задеть
  встречного, иначе догорает. В таблице весов у лидера ракета = 0.
- Подбор при занятом слоте: бокс остаётся стоять, события `pickup` нет.
- Применение при исчерпанном `MAX_PROJECTILES`: бонус остаётся в руках,
  события `use` нет. Молча съедать бонус нечестно по отношению к игроку.
- Пустой список `items` при `items_enabled: true` равносилен выключенным
  бонусам: боксы не показываются и не подбираются.
- Кнопка применения — по фронту, с защёлкой: между тиками приходит несколько
  пакетов ввода, без защёлки короткое нажатие терялось бы.
- Таблица весов задана на восемь мест, а ехать может и трое: место
  растягивается на восемь строк. Гонка в одиночку попадает в середину
  таблицы, а не в оборонительную строку лидера.

**Семантика `CarState.lap`.** Решётка стоит позади линии старта, поэтому
первое её пересечение даёт `lap = 0`. «Проехать N кругов» — это `lap >= N`.
Поле `lap` в событии `lap` — номер **пройденного** круга.
`results.time` при `dnf: true` — общее время гонки.

**Каталог машин для симуляции.** `Simulation(track, settings, players)`
получает только `car_id`, а характеристики лежат в `content/cars.json`.
Симуляция читает файл рядом с пакетом и кэширует, но при запуске сервера
с `--content` на другой каталог это разъехалось бы. Поэтому сервер обязан
позвать `game.sim.set_car_catalog(catalog)` тем же каталогом, который он
раздаёт клиентам. Реализовано в `server/room.py`.

**Баланс — измеренный, а не назначенный.** 24 гонки, три трассы на восьми
зёрнах, восемь ботов:

| | без бонусов | с бонусами |
|---|---|---|
| смен лидера за гонку | 1,96 | **2,79** |
| сдвиг мест от середины дистанции к финишу | 0,12 | **1,57** |
| разрыв между первым и последним | 7,7 с | 18,4 с |

Попаданий в лидера — 0,67 за гонку, ещё 0,50 гасит его щит. То есть лидера
сбивают примерно раз в четыре минуты, а не раз в десять секунд, но порядок
к финишу всё равно перетасовывается на полтора места вместо одной десятой.
Это и есть искомое: отставший имеет шанс, лидер не беспомощен.

Веса подбирались итерациями по замеру. Первый вариант (у лидера 46/38 на мину
и щит, ракета у второго места 8) давал недосягаемого лидера — бонусы вообще
ничего не решали. Промежуточный с ракетой 28–30 давал 14 раскруток за гонку,
что уже слишком.

Замеренная цена эффектов (потеря прогресса за 6 с относительно базы 32,1 м/с):
турбо 2,5 с даёт +0,81 с, ракета −3,18 с, мина −3,0 с, гроза −0,43 с каждому
впереди. Длительность раскрутки почти не важна: цена в потере управления,
а не в секундах — даже 0,5 с стоит 2,34 с.

**Замеренное время тика:** сама симуляция 0,054 мс в среднем (p99.9 — 0,137 мс),
живая комната на восьми клиентах вместе с рассылкой 0,161–0,198 мс,
то есть 8–10 % бюджета в 2 мс. Разбивка: физика восьми машин 0,042 мс,
бонусы и столкновения 0,016 мс, снапшот 0,002 мс.

### 12.11. Рендер: бюджет, владение клавишами и подводные камни three.js

**Измеренный бюджет** (1280×720, восемь машин, худший случай — все дрифтуют,
турбо, вне трассы, под щитом, тормозят, четыре ракеты, четыре мины, взрывы):

| тема / пресет | draw call | треугольники |
|---|---:|---:|
| city / high | 54 | 90 222 |
| industrial / high | 56 | 93 036 |
| mountain / high | **57** | **134 704** |
| абсолютный потолок (все восемь у стартовой арки) | **58** | **135 286** |

Потолок 60 и 150 000 держится с запасом в два вызова и около 10 %
треугольников. Вид из кокпита дешевле на два вызова: панель и руль стоят
плюс два, а своя машина в этом виде скрывается (иначе видны изнаночные
грани кабины) и возвращает четыре.

**Где лежит бюджет.** Восемь машин — это 32 вызова, больше половины всего
кадра: `buildCarMesh` отдаёт по четыре меша на машину (кузов, колёса, фары,
стопы). Тени, боксы и все эффекты вместе — ровно 7 вызовов, а в спокойной
гонке 2–4, потому что меш с нулём инстансов прячется.

**Резерв, если бюджет когда-нибудь не сойдётся:** слить фары и стоп-сигналы
в геометрию кузова эмиссивными вершинными цветами. Это вернёт 16 вызовов
из 60 — самый дешёвый ход, который у нас есть. Второй, помельче: облака
в `scenery.js` сделаны `transparent` + `DoubleSide` и потому рисуются
в два прохода; одна строка `forceSinglePass = true` вернёт ещё один вызов.

**Тема mountain на пресете high почти исчерпана по треугольникам:**
трасса 41 216 плюс декор 83 648 — это 124 864 из 150 000 ещё до машин
и эффектов. Добавлять геометрию в эту тему больше некуда.

**Подводные камни three.js r180**, найденные опытным путём:

- Материал с `transparent: true` и `side: DoubleSide` рисуется **в два
  прохода**, если не выставить `forceSinglePass = true`. Нигде не
  документировано, стоит лишних draw call.
- `instanceColor` доходит до фрагментного шейдера только при
  `material.vertexColors === true`, и у геометрии инстанса обязан быть
  атрибут `color` из единиц. Иначе частицы либо чёрные, либо игнорируют
  инстансный цвет.

**Владение клавишами.** `C` (смена камеры) и `Shift` (взгляд назад)
обрабатывает **рендер**, по той же схеме, что `Tab` и `F3` у интерфейса.
`input.js` их НЕ трогает. У рендера есть `{bindKeys: false}` и наружу
выставлены `toggleCamera`, `setCameraMode`, `setLookBack`.

**Две разные очистки.** `dispose()` разбирает сцену, пулы и кэш чертежей,
но оставляет контекст WebGL живым — это возврат в лобби. `destroy()`
дополнительно зовёт `renderer.dispose()` и отвязывает клавиши — это выход
со страницы. Проверено пятью циклами сборки и разборки сцены: геометрии,
текстуры и программы возвращаются в ноль, куча не растёт.

**Что обязан делать `main.js`.**

- Звать `setCatalog(welcome)` из `cars.js` **до** `createRace`: в
  `race_init.players[]` есть только идентификатор машины, а рендеру нужна
  форма.
- Звать `rr.hitCar(slot)` при `race_event kind:"hit"` с `blocked: false`
  и `rr.shieldBlock(slot)` при `blocked: true`. **Событие `hit` не несёт
  координат**, взрыв рисуется по позиции пострадавшей машины.

### 12.12. Пауза, прогрев отсчёта и эпоха серверных часов

**Глобальная пауза.** Живёт поверх `RACING` и состояние комнаты не меняет.
Ставит и снимает **любой участник гонки** — клавишей `P` или кнопкой в HUD,
быть владельцем комнаты не нужно: это офисная игра, а не турнир.

На паузе комната останавливает игровой цикл целиком, поэтому замирают разом
время гонки, времена кругов, снаряды, таймеры бонусов, `FINISH_GRACE`
и `RACE_TIMEOUT` — морозить их поштучно не пришлось. Ввод не принимает ни
сервер, ни клиент: кадровый цикл не делает ни одного фиксированного шага,
и своя машина замирает ровно там, где её застала пауза.

Снятие идёт через обратный отсчёт `PAUSE_RESUME_SECONDS = 3` обычными
событиями `countdown`; тик стоит до самого нуля. Ограничения:
`PAUSE_MIN_INTERVAL = 20` с на игрока (иначе ошибка `pause_rate`) и общий
бюджет простоя `PAUSE_MAX_TOTAL = 300` с на гонку, после исчерпания пауза
снимается сама с `reason: "timeout"`.

```jsonc
{"t":"pause","phase":"paused",  "by":2,"name":"Вася","reason":"player","budget":287.4}
{"t":"pause","phase":"resuming","by":2,"name":"Вася","reason":"player","budget":284.1,"resume_in":3}
{"t":"pause","phase":"running", "by":2,"name":"Вася","reason":"player","budget":281.0}
{"t":"pause","phase":"running", "by":-1,"name":"", "reason":"timeout","budget":0.0}
```

`phase` — `paused` | `resuming` | `running`; пока фаза не `running`, комната
не тикает. `by` — слот инициатора, `-1` если сняла система. `reason` —
`player` | `timeout` | `race_over`. `budget` — сколько секунд простоя ещё
разрешено. Клавишу `P` обрабатывает `ui/hud.js`, `input.js` её НЕ трогает.

**Отсчёт прогревает клиента.** Все три секунды `COUNTDOWN` комната рассылает
снапшоты решётки на 20 Гц. Без этого клиент приходил к старту с пустой
историей интерполяции.

**Эпоха серверных часов — причина дёрганья на старте.** Клиент привязывает
местные часы к серверным как минимум по окну из 64 замеров `приход − tick·DT`.
Равенство `tick·DT == race_time` (12.4) верно **только пока симуляция тикает**.
Единственный снапшот решётки с `tick = 0`, отправленный за 2,5 с до того, как
серверные часы пошли, давал заниженный замер — и, будучи минимумом, держал
оценку заниженной все 64 замера, то есть 3,2 с. Момент отрисовки уезжал на
2,4 с новее самого свежего снапшота, пара для интерполяции не находилась,
и чужие машины показывались экстраполяцией с постоянной позицией между
снапшотами: те самые ступеньки раз в 50 мс. Ровно на 3,2-й секунде минимум
вытеснялся из кольца, оценка скачком исправлялась, и всё «становилось нормально».

Правило: **в окно оценки смещения попадают только снапшоты идущей симуляции.**
Снапшоты с замороженным тиком (отсчёт, пауза) размечаются по времени прихода —
шкала истории остаётся непрерывной, оценка не отравляется. Плюс страховка на
непредвиденную смену эпохи: если сырой замер держится выше оценки дольше
`CLOCK_RESYNC_GAP` подряд `CLOCK_RESYNC_HITS` раз, окно строится заново.
Простой паузы вычитается из местных часов.

Измерено (отклонение позиции чужой машины от гладкой траектории, p95, метры):

| секунда гонки | до правки | после |
|---|---|---|
| 0 | 0,339 | **0,0017** |
| 1 | 0,562 | **0,0022** |
| 2 | 0,668 | **0,0015** |
| 3 | 0,700 (пик 3,98) | **0,0005** |

**Экран итогов.** Кнопка «В лобби» только пропускает таблицу вперёд:
`teardownRace()` плюс экран лобби, **без выхода из комнаты**. Через 15 с
сервер сам переводит комнату в `LOBBY`. Вешать эту кнопку на выход из комнаты
нельзя: игрока уносило в меню, а если жал владелец — комната ещё и меняла

### 12.13. Итоги плейтеста: ручник, столкновения, баланс

**Ручной тормоз вместо «дрифта».** Заказчик на плейтесте: «дрифт слишком
резкий и неуправляемый, не подходит для поворотов, работает только при
зажатой A или D». Всё три замечания справедливы, механика переработана:

- требование зажатого руля (`DRIFT_STEER_MIN`) **снято** — ручник срабатывает
  от одного пробела;
- поворот стал управляемым: усиление 1,55 → 1,18, потолок скольжения 27° → 20°,
  плюс ручник подчиняется тому же пределу по сцеплению, только поднятому
  в `HANDBRAKE_LAT_GAIN` раза;
- ручник **тормозит** на `HANDBRAKE_DECEL = 9` м/с² — раньше он только снижал
  боковое сцепление, и название не соответствовало поведению;
- закрыта дыра: без требования по рулю «зажать пробел на прямой» давало бы
  бесплатное ускорение, поэтому заряд копится только за настоящий занос.

Замер: было — разворот в 1,53 раза круче сцепления практически даром.
Стало — поворот в 1,45 раза круче ценой четверти скорости, ловится
за 0,20–0,25 с. Шпилька радиусом 13 м проходится на 21,2 м/с вместо 19,0.
Это «вписаться в поворот», а не «крутануться».

Внутренние имена переименованы в `HANDBRAKE_*`. **Поля протокола остались:**
`drift_charge` в снапшоте и бит 1 «дрифтует» — часть бинарного формата,
их читают рендер, HUD и звук.

**Потолок скорости.** Проверка каталога в `game/cars.py` ограничивала
фактический потолок 55 м/с (198 км/ч), и это упиралось ровно туда, куда
балансировщик уже дотянул машины. Граница поднята до 70 м/с (252 км/ч);
это проверка вменяемости, а не игровая настройка, и текущие машины
используют только до 197 км/ч.

**Дубль константы.** В `game/track.py` лежала своя копия `CAR_RADIUS = 1.1`
«из 6.4». При смене формы столкновений на капсулу числа молча разъехались.
Копия переименована в `GRID_HALF_WIDTH` и отвязана от раздела 6.4: она
описывает запас по ширине на стартовой решётке, а не форму столкновения.

**Скорость ракеты** (12.10) больше не константа: `items.rocket_speed()`
выводит её из каталога машин. При этом обнаружилось, что равновесие тяги —
неверная оценка потолка для машины на ускорении: шаг 7 тянет скорость
**прямо** к `boost_speed`, минуя формулу тяги. Учтено, ракета 83,2 м/с
против 65 м/с у лидера на «Турбо».

**Замеры после переработки:** шаг физики 1,46 мкс, восемь машин 0,018 мс
на тик; полный тик симуляции — медиана 0,088 мс, p99 0,15–0,23 мс при
бюджете 2 мс. Расхождение Python и JS 2,7e-13 м. Проверок в тесте гонки
стало 120.

### 12.14. Графика после плейтеста

**Бюджет пересмотрен.** Плейтест на целевом N5105 дал 100 fps на высоком
пресете — вдвое больше, чем закладывал контракт. Новая цель: не ниже 60 fps
на высоком, низкий пресет остаётся быстрым.

Фактические максимумы после доработки: **50 draw call, 151 тыс. треугольников**
(`ridge` на высоком). Низкий пресет стал **быстрее**, чем был: свечение
и анимация им выключены, а облака получили `forceSinglePass` (12.11) —
минус проход и минус шейдерная программа.

**Запечённое затенение** считается один раз при сборке сцены и кладётся
в вершинные цвета: в кадре стоит ноль. Сборка сцены подорожала в 1,05–1,55
раза (типично 1,25) — на целевом железе это примерно 8–11 мс на исходных
трассах и 15–18 мс на новых длинных. У машины затенение кладётся в **базовый**
цвет чертежа, поэтому цвет игрока умножается на уже затенённую базу
и тень не пропадает при перекраске.

**Свечение — геометрией, не постобработкой.** Полноэкранный bloom на UHD 24 EU
означает второй фреймбуфер в разрешении экрана плюс проходы размытия.
Вместо него один `InstancedMesh` с аддитивными билбордами: **+1 draw call
на всю сцену**, при нуле ореолов меш прячется.

**Анимация декора — целиком в вершинном шейдере** через `onBeforeCompile`
и общий uniform времени. Фаза берётся из матрицы инстанса, поэтому соседние
объекты качаются вразнобой без единого дополнительного атрибута. Для
процессора это одна запись числа в кадр.

**Отсечение по пирамиде видимости сделано, нормировка плотности снята.**
Раньше декор и лента рельефа отправлялись в кадр целиком, и каждая тысяча
метров длины стоила 45–50 тыс. треугольников независимо от того, что игрок
видит. Приходилось разжижать длинные трассы — лечение симптома. Теперь длина
трассы треугольников не стоит, и `DECOR_REF_LENGTH` с `TERRAIN_REF_LENGTH`
удалены.

### Расширения интерфейсов рендера

Все новые параметры необязательные, без них поведение прежнее.

```
buildTrackMeshes(track, theme, quality, opts)   // opts: {ao}
buildScenery(track, theme, seed, quality, opts) // opts: {ao, decor, anim}
buildCarMesh(shape, color, quality, opts)       // opts: {ao}
```

`buildScenery` дополнительно возвращает `animated` и `updateAnim(t)`.
**Рендер обязан звать `updateAnim` каждый кадр** — так же, как `updateSky`.

`buildCarMesh` возвращает `lamps: {head, brake, exhaust}` — плоские массивы
`x, y, z, размер` в системе координат машины, якоря накладного свечения.

`Effects` получил `setGlowEnabled(on)` и `setHiddenSlot(slot)`. Второй
обязателен: в виде из кокпита своя машина скрыта, и её ореолы надо гасить,
иначе фары светят прямо в объектив.

В `effects.js` теперь **шесть** инстансированных мешей, а не пять: добавился
меш свечения.

### 12.15. Второй плейтест: эксплойт с зарядом заноса

Заказчик дословно: «мы можем зажать ручник и просто нажимать A/D, едем
не быстро но очки бонуса дрифта набираются и дают скорость, это абуз».

Первая правка (12.13) закрыла только «зажать пробел на прямой», потребовав
настоящего бокового скольжения. Но на малой скорости скольжение достигается
перекладыванием руля почти даром. Поставлено **три независимых барьера**:

1. **У заноса есть сторона.** Поле `drift_dir`; смена знака обнуляет заряд.
   Виляние A→D→A физически перестаёт копить. Около нуля — зона
   нечувствительности `HANDBRAKE_FLIP_SLIP`, вдвое уже порога накопления,
   чтобы дрожание руля не роняло честный занос.
2. **Темп накопления зависит от скорости**, квадратично, от нуля на
   `HANDBRAKE_MIN_SPEED` до полного на `HANDBRAKE_CHARGE_FULL_SPEED`.
   Барьер работает и в одиночку: без стороны виляние даёт 3,3–4,3 с
   вместо 9,9.
3. **Вне трассы заряд не копится.** Одна проверка закрывает и занос
   по газону, и выталкивание стеной.

Замеры (порог уровня 1 — 0,70 с заряда):

| сценарий, 10 с | было | стало |
|---|---|---|
| виляние A/D, период 1,0 с | 7,63 | **0,44** |
| слалом ±12°, период 1,0 с | 7,63 | **0,29** |
| слалом ±12° на 25 м/с | 7,40 | **0,55** |
| занос об стену | 0,28 | **0,00** |
| занос по газону | 1,42 | **0,00** |

Честный занос почти не пострадал: длинные дуги дают уровни 1, 2 и 3 ровно
за те же 0,90 / 1,60 / 2,62 с. Шпилька радиусом 13 м дорожает на третьем
уровне на 1,15 с, а медленный поворот на 15 м/с третьего уровня больше
не даёт — это сознательная цена, потому что именно на таких скоростях
и жил эксплойт.

**Не закрыто сознательно:** двое игроков, непрерывно трущиеся бортами
10 секунд на 20 м/с, выжимают жертве 0,83 с заряда — один буст первого
уровня. Закрыть можно только флагом «меня толкнули», а его выставляет
серверная `resolve_collisions`, которую клиент принципиально не
предсказывает (6.2). Поле развалило бы паритет предсказания ради заведомо
убыточного трюка: нужен второй игрок, теряющий больше.

**Тест на эксплойт постоянный.** В `tools/test_physics_parity.py` добавлены
16 проверок: семь вариантов виляния и слалома, прямая проверка обнуления
при смене стороны, занос задним ходом, об стену и по газону — и пять
проверок с другой стороны, что честные дуги по-прежнему дают все три уровня.
Вторая половина нужна не меньше первой: без неё «защиту» чинят выключением
награды. Проверено, что тест падает на старом коде.

Заодно сверка Python и JS теперь охватывает сам `drift_charge` (расхождение
2,4e-15 с). Раньше заряд не сверялся вовсе, а он не двигает машину до
выдачи буста — разъехавшаяся ветка могла прятаться долго.

**Кольцо предсказания в `net.js` обязано хранить `drift_dir`.** Без этого
после реконсиляции сторона отстаёт от переигранной истории и может на тик
сжечь честную копилку.

### 12.16. Отсечение видимости и время суток

**Как устроено отсечение.** Декор отсекается **по инстансам**: экземпляры
раскладываются по корзинам вдоль дуги трассы (около 45 м на корзину), в кадре
проверяется сфера корзины, видимые копируются подряд одним прогоном и
выставляется `count`. Корзина дёшева именно потому, что трасса — замкнутая
дуга, а декор живёт узкой полосой вдоль неё: одномерная раскладка по
пройденному пути описывает пространство не хуже сетки, а стоит одно деление.
Объекты без привязки к дуге (горные пики) уходят в свободный хвост и
проверяются поштучно — их два десятка.

Полотно и рельеф режутся на сегменты примерно по 180 м. Швов нет по
построению: соседние сегменты делят общий ряд выборок из одних и тех же
чисел. Видимые сегменты склеиваются в прогоны и уходят в `geometry.groups`
(материал задан массивом — единственная ветка three.js r180, где `groups`
читаются), максимум три прогона на меш.

Результат: треугольники в худшем случае **151 тыс. → 78 тыс.**, вызовы
отрисовки 50 → 49. По всем пятнадцати замерам суммарно 1 350 134 → 704 100,
то есть вдвое. Процессорная часть кадра подорожала на 0,1 мс — это цена
проверки, и она окупается кратно.

**Корректность проверена сравнением кадров, а не на глаз.** Кадровый цикл
замораживается, одна сцена рисуется с отсечением и без, холст сравнивается
попиксельно: 156 видов (по всему кругу, у кромки, с развёрнутой камерой,
из кокпита, со взглядом назад; пять трасс, три пресета) — **расхождение
0,0000 % везде**. По дороге это вскрыло три настоящих бага, которых глазами
было не поймать: отсечение по радиусу вместо глубины вдоль взгляда (туман
линеен по глубине, на краю кадра радиус в полтора раза больше, и объекты
срезались раньше тумана); аддитивный материал с `fog: true` гаснет не в ноль,
а прибавляет цвет тумана; низ купола неба не совпадал с цветом тумана.

**Путь поля времени суток целиком:** файл трассы → `Track.to_client()`
и каталог в `welcome` → `settings.time_of_day` в комнате → `room` и `race_init`
→ `main.js` → `createRace({env})` и `setEnvironment()`. Клиент передаёт рендеру
**настройки комнаты целиком**, а не выкушенное поле: объект плоский и лишнее
игнорирует, поэтому погоде отдельная проводка не понадобится.

Валидация окружения на сервере сведена в таблицу `config.ENV_FIELDS` — строка
под погоду там уже лежит закомментированной, и её включение не требует ни одной
новой строки в `room.py`.

**Время суток приходит параметром, а не из трассы.** `day | dusk | night`,
сумерки считаются интерполяцией между дневной и ночной таблицей темы.
Погода ляжет на тот же механизм — те же поля (небо, туман, свет, яркость
огней), накладываемые поверх.

```
buildTrackMeshes(track, theme, quality, {ao, timeOfDay})
buildScenery(track, theme, seed, quality, {ao, decor, anim, env, nightLights})
RaceRenderer.createRace(track, players, {env})
RaceRenderer.setEnvironment(env)
```

Форма объекта окружения — плоская, лишние поля игнорируются, неизвестные
значения заменяются умолчанием, поэтому можно слать настройки комнаты целиком:
`{ time_of_day: 'day'|'dusk'|'night', weather: 'clear'|... }`.
Понимаются и `timeOfDay`, и `time_of_day`, и голая строка.

**Обе функции возвращают `cull(culler)`, и рендер обязан звать его каждый
кадр** после обновления матриц камеры — наравне с `updateSky` и `updateAnim`.
`buildTrackMeshes` и `buildScenery` обязаны получать не только один и тот же
`quality`, но и **одно и то же время суток**, иначе палитра полотна разойдётся
с небом и светом.

**Ночь.** Тёмное небо со звёздами и луной одним мешем, холодный лунный свет,
тёмно-синий туман ближе дневного. Фонари светят конусом из двух вложенных
оболочек (поперечный градиент без шейдера) плюс пятно на асфальте. Окна в
зданиях горят детерминированным по seed рисунком, щиты подсвечены. Фары
становятся главным источником: эмиссив втрое ярче плюс `beamMesh` — пятно
света на асфальте, один `InstancedMesh` на восемь машин, днём не строится.
Разметка получила слабый эмиссив: без световозвращающей краски полотно
в свете фар читается как чёрная яма. Вспышки взрывов наоборот придержаны
на 18 %, иначе аддитив по тёмной сцене выбивает белое.

Ночь стоит +4 вызова отрисовки и около 8 % треугольников.
Уличное освещение сделано для тем `city` и частично `industrial`;
у `mountain` его нет намеренно — горная дорога без фонарей правдоподобна.

**Новые настройки:**

| настройка | ключ | значения | low / medium / high |
|---|---|---|---|
| Дальность отрисовки | `racing.gfx.viewdistance` | near / normal / far | near / normal / far |
| Яркость ночных огней | `racing.gfx.nightlights` | off / normal / bright | normal / normal / bright |
| Время суток | `racing.gfx.timeofday` | auto / day / dusk / night | auto / auto / auto |

`auto` означает «как выбрано в комнате». Дальность правит туман, дальнюю
плоскость камеры и предел отсечения одним числом — иначе отсечение перестаёт
быть бесплатным — и применяется без пересборки сцены.

**Ещё два подводных камня three.js r180:** `onBeforeCompile` получает исходник
**до** раскрытия `#include`, поэтому подменять надо сам include; аддитивный
материал с `fog: true` гаснет в цвет тумана, а не в ноль — для свечения это
неверно и ломает отсечение по дальности.

### 12.17. Как читать результат сквозного автотеста

`tools/smoke_test.py` меряет, **успевает ли клиент**. Метрики плавности чужой
машины и сходимости позиций поэтому чувствительны к загрузке машины, на
которой идёт прогон: на занятом стенде браузер роняет шаги, интерполяция
честно деградирует, и тест краснеет, хотя игра цела.

**Правило, выведенное из ошибки дирижёра.** Красный прогон не считается
доказательством, пока не сверена загрузка машины. И два прогона **нельзя
сравнивать между собой, если они сняты в разное время при меняющейся
нагрузке** — это сравнение времени, а не кода.

Случай: правки графики были объявлены регрессией на основании двух прогонов,
базового и изолированного. Базовый попал на спокойную машину, изолированный —
на пик загрузки 18–20 от параллельной сборки Rust и нескольких браузеров.
На спокойной машине то же самое дерево дало 34 из 34. Исполнитель успел
потратить время на поиск несуществующей причины.

Тест сам подсказывает ответ: справочная строка «то же в лоб» печатает число
**пропущенных шагов за гонку**. В зелёном прогоне это около сотни, в ложно
красном — втрое больше. Смотреть на неё до выводов, а не после.

**Порог измерен.** Десять прогонов, чередуя два дерева: при 40 кадрах в
секунду и выше зелено четыре раза из четырёх, при 35 и ниже красно шесть
из шести, между этими значениями ничего не наблюдалось. Причём **чистый
HEAD падает с точно такой же подписью** — это и закрыло вопрос об авторстве.

Правило: **запускать только когда первое число в `/proc/loadavg` ниже 1,0.**
Пауза в восемь секунд между прогонами не спасает — средняя загрузка спадает
минутами, и следующий прогон стартует в яму. Тест теперь проверяет загрузку
сам и печатает предупреждение, если она выше порога.

Изолировать чужие правки — разворачивая коммит через `git archive` во
временный каталог, **и оба сравниваемых прогона делать подряд**, на одной
и той же загрузке.

**Время кадра, снятое из JS, в этой среде измеряет не то.** Команды WebGL
в Chromium уходят в отдельный процесс, растеризация происходит там, и
`performance.now()` вокруг кадра в главном потоке застаёт только отправку
команд. Замер таким способом давал «одно дерево быстрее на 24 %» — чистый
артефакт. Настоящую цену видит только счётчик кадров через
`requestAnimationFrame`, и то при двух условиях: не упираться в вертикальную
синхронизацию (на 480×320 оба дерева дают ровно 60,0 и замер бесполезен)
и брать лучшее из нескольких повторов. На честной нагрузке 1280×720 разница
между сравниваемыми деревьями оказалась 0,2 %.

**Операционная ловушка.** `pkill -f 'pw-browsers/chromium-1194'` одной
строкой из оболочки **убивает собственную оболочку**: шаблон присутствует
в её же командной строке. То же самое случается с `ps | grep` по имени
запущенного процесса. Уборку класть в отдельный файл-скрипт, шаблон держать
в переменной.

### 12.18. Этап 2: трамплины, полёт и крюк под покрытие

Принято по отчёту исполнителя, проверено лично: паритет Python↔JS не сдвинулся
ни на разряд (позиция 2,675e-13 м, как было), тест паритета зелёный на 41
постоянной проверке (было 23), таблица `WEATHER_GRIP` совпадает во всех трёх
местах, запрещённой математики в шаге нет.

#### Новые поля состояния (дополнение к 6.1)

| поле | смысл |
|---|---|
| `height` | высота над полотном, м. Ноль — колёса на земле |
| `v_vert` | вертикальная скорость, м/с |
| `airborne` | признак полёта |
| `land_stun` | остаток времени без управления после жёсткой посадки, с |
| `ramp_h` | высота полотна трамплина под машиной; пишет `clamp_to_track` каждый шаг |
| `grip_mul` | множитель сцепления, по умолчанию 1,0 |

`ramp_h` и `grip_mul` — **самовосстанавливающиеся**: первый переписывается
каждый шаг, второй не меняется за окно переигровки. Остальные четыре несут
состояние между шагами и **обязаны** сохраняться в кольце предсказания
`net.js` наравне с `drift_dir` (12.15). Без этого машина приземляется посреди
прыжка после реконсиляции.

#### Шаг 14б: вертикальная ось (дополнение к 6.2)

Три ветки:
* **в воздухе** — `v_vert -= GRAVITY*dt`, `height += v_vert*dt`, проверка посадки;
* **на полотне трамплина** — `v_vert = (ramp_h - height)/dt`, `height = ramp_h`;
* **кромка** — полотно кончилось, машина наверху: отрыв, `v_vert` зажат
  `RAMP_LIFT_MAX`.

Правки существующих шагов: 1 — `land_stun` глушит ввод целиком (но НЕ крутит
машину, в отличие от `spin_time`), в воздухе глушатся газ, тормоз и ручник,
руль остаётся; 7 и 8 — в воздухе «Турбо» не тянет и «Гроза» не тормозит, но
их таймеры тикают; 9 — в воздухе поворот идёт с `AIR_TURN_GAIN` без предела
по сцеплению, на земле предел домножен на `grip_mul`; 10 и 11 — в воздухе
пропущены целиком, на земле `grip_step` домножен на `grip_mul`; 14 —
`clamp_to_track` не выталкивает в полёте и снимает `offtrack`; 15 — условие
сжигания копилки заноса теперь `spinning or airborne`.

**Почему в полёте не уводит траекторию.** Шаг 5 раскладывает скорость в
базисе шага 4, шаг 12 собирает обратно в том же базисе, шаги 10 и 11 между
ними пропущены — алгебраически это тождество. В float64 круг «разложить и
собрать» стоит ~1e-16 на шаг, то есть 7,5e-14 м/с за весь полёт. Поэтому руль
в воздухе крутит только курс.

#### Новые константы (дополнение к 6.4)

`GRAVITY = 12.0`, `RAMP_LIFT_MAX = 6.5`, `AIR_TURN_GAIN = 0.14`,
`LAND_SLIP_FACTOR = 0.55`, `LAND_HARD_SPEED = 10.5`, `LAND_SPEED_LOSS = 0.055`,
`LAND_KEEP_MIN = 0.55`, `LAND_STUN_TIME = 0.35`, `GRIP_MUL_MIN = 0.25`,
`GRIP_MUL_MAX = 2.0`; в `track.py` — `RAMP_EDGE = 1.0`.

#### Поле `ramps` в описании трассы (дополнение к 7.1)

```json
"ramps": [{"at": 0.205, "angle": 12, "rise": 1.25, "half_width": 4, "offset": 1.6}]
```

`at` — доля круга, на которой стоит кромка вылета (въезд ПЕРЕД ней);
`angle` — угол въезда в градусах, 3..20; `rise` — высота кромки, 0,2..3,0 м;
`half_width` — половина ширины, не меньше 1,5 м; `offset` — смещение от оси,
плюс влево (раздел 4), необязательное. Длина въезда **выводится**:
`length = rise / tan(angle)`, тангенс считается один раз на загрузке — в шаге
физики тригонометрии нет. Валидация требует `|offset| + half_width <= width/2`:
трамплин обязан помещаться в полотно.

В `Track.to_client()` (12.1) едет **выведенная** геометрия (`s0`, `length`,
`slope`, `offset`, `half_width`, `rise`), а не исходное описание — клиент
обязан получить те же числа, что считает сервер.

В интерфейс `Track` (7.3) добавлен `ramp_height(index, lateral, along)`. Своего
поиска ближайшей точки он не делает, работает на том, что посчитал
`clamp_to_track`, поэтому трамплин стоит **ноль** дополнительных обращений к
трассе: на карте без трамплинов это одна запись нуля в поле.

Расставлено 4 трамплина на 3 трассах: `serpentine` 1, `industrial` 1,
`ridge` 2. `office` и `avenue` намеренно не тронуты — `office` остаётся
широкой и прощающей картой для новичков.

#### Крюк под покрытие (дополнение к 12.5)

`state.grip_mul` (JS `state.gripMul`), по умолчанию 1,0. Владелец погоды
пишет одно число каждой машине на своей стороне; **в бинарном снапшоте под
него не нужно ни бита** — значение приезжает тем же JSON-событием, которым
включается погода.

```
WEATHER_GRIP = {'clear': 1.0, 'wet': 0.86, 'snow': 0.72, 'fog': 1.0}
```

Таблица повторена в **трёх** местах: `server/config.py`, `game/physics.py`,
`static/js/physics.js`. Числа обязаны совпадать до последнего разряда —
расхождение даёт не косметику, а рассинхрон предсказания с сервером. В тест
паритета добавлена машинная сверка таблицы Python↔JS.

Замерено на Хэтче: сухо 27,61 м/с² поперечного, мокро 23,74 (−7,3 % скорости
в дуге R=30 м), снег 19,88 (−15,1 %). Для сравнения, разница между самой
цепкой и самой скользкой машиной каталога — 12 % (12.7). То есть мокрый
асфальт это «надо аккуратнее», снег — «надо по-другому».

`reset()` поле намеренно НЕ трогает: `reset` обнуляет движение, а покрытие под
колёсами к движению не относится. Значение зажимается в `[0.25, 2.0]` один раз
за шаг — защита шага 10 от чужого нуля или двойки, при которых множитель
`(1 - grip_step*grip_mul)` уходит в минус и боковая скорость меняет знак
каждый шаг.

**Почему в состоянии, а не в характеристиках машины.** `game/sim.py` кормит
шаг объектом `CarSpec` из `game/cars.py` с одиннадцатью полями из
`STAT_LIMITS`, и двенадцатое не завести, не тронув чужой модуль. Хуже того,
`server/room.py` собирает гандикап перебором `physics.CarStats.__slots__` с
`getattr`, а ошибку глотает в `except Exception`: лишний слот **тихо отключил
бы гандикап**. Это известная хрупкость, её стоит развязать отдельно.

**Задел на покрытие участком трассы.** Если гравий или грунт станут свойством
участка, а не всей гонки, писать `state.grip_mul` будет `clamp_to_track` —
там же, где он уже пишет `offtrack` и `ramp_h`. Шаг при этом не меняется ни на
строку, а поле остаётся самовосстанавливающимся.

#### Баланс и эксплойт

Баланс не тронут: разброс среднего круга по пяти машинам 0,350 % → **0,341 %**
(по квазистатической модели исполнителя, которая воспроизводит фаворитов из
12.7 в точности). Фавориты по трассам не перетасовались. Трамплины стоят всем
машинам примерно поровну, +0,09…+0,26 с на круг.

К трём барьерам эксплойта 12.15 добавлен **четвёртый**: в воздухе ручник
заглушён (шаг 1), а шаг 15 сжигает копилку без награды. Замерено: ручник и
полный руль весь полёт дают пик заряда 0,000 с; копилка 3,00 с, принесённая на
кромку вылета, даёт 0 ускорений и остаток 0,00 с.

**Прыжок не бесплатный ускоритель.** В воздухе нет ни тяги, ни сопротивления,
поэтому машина, не дошедшая до потолка скорости, теряет разгон, который
сделала бы на земле — за 1,23 с полёта это +5,7 м/с, которых не будет. Скорость
на заходе не наказывается вообще; наказывается перекос при посадке: 10° стоят
−11 % и 0,35 с без управления, 20° — −34 %. Слабый руль в воздухе (полный лок
за весь полёт даёт 21,4°) оставлен намеренно: этого хватает выровнять машину
и не хватает её развернуть. Срезать трассу прыжком нельзя — 40–55 м полёта не
перепрыгивают ни одной из 12 отсечек на круг.

### 12.19. Этап 2: погода как настройка комнаты

Принято по отчёту исполнителя. Значения: `clear | wet | snow | fog`, умолчание
`clear`, правило при смене карты — то же, что у `time_of_day`. Код ошибки
`bad_weather` из 12.6 больше не «зарезервирован», он в работе.

#### Заявка «раскомментировать — и заработает» подтвердилась

В `config.ENV_FIELDS` раскомментированы `WEATHERS` и строка погоды. **Ни одной
новой строки в `room.py` не понадобилось** — это проверено, а не обещано.
Бесплатно заработали: проверка значения, умолчание из описания трассы (у трассы
поля нет, `getattr` отдаёт `clear`), попадание в `settings`, `room`,
`race_init` и в `welcome.content.tracks[]`, потому что каталог собирается тем
же циклом.

Это оправдывает табличный вид `ENV_FIELDS`, заложенный в 12.16: новое поле
окружения стоит одну строку. Следующее (покрытие, ветер) обойдётся так же.

#### Обе половины крюка сцепления обязаны включаться вместе

Клиент: `main.js` зовёт `applyWeatherGrip(settings)` из `onRoom` и из
`onRaceInit`, пишет `net.state.gripMul` **присваиванием**, а не умножением —
событие `room` приходит и по ходу гонки. Своей таблицы в `main.js` нет,
там именованный импорт из `physics.js`.

Сервер: одна строка в `Simulation.__init__` рядом с `track.init_state`:

```python
car.state.grip_mul = physics.WEATHER_GRIP.get(self.settings.get('weather'), 1.0)
```

**Пока серверной строки нет, клиент предсказывает со сниженным сцеплением, а
сервер считает по сухому — в поворотах машину оттягивает реконсиляцией.**
Машинам траффика множитель нужен тоже, иначе по мокрой трассе болванки поедут
цепче игроков.

#### Осадки в `scenery.js`

Один меш на сцену: **+1 вызов отрисовки, ~4,3 тыс. треугольников** (1066
частиц × 4). Движение — падение, заворот, снос, покачивание снежинок —
целиком в вершинном шейдере от общего uniform времени; коробка осадков ездит
за камерой внутри уже существующего `updateSky`. **Процессорная цена в кадре —
ноль.**

Плотность: пресет качества (0,5 / 0,8 / 1,0) × `racing.gfx.particles`
(`off` / 0,55 / 1,0 / 1,3). Значение `off` снимает меш полностью — ноль вызовов
и ноль треугольников. Новой галочки не заводилось, требование «всё новое
отключается» закрыто существующей настройкой; в таблице 12.14 у
`racing.gfx.particles` теперь есть и это назначение.

**Погода накладывается обесцвечиванием с потемнением, а не подмешиванием
фиксированного серого.** Это не косметическая деталь: с подмешиванием серого
ночное небо светлело, и дождливая ночь выходила светлее ясной. Обесцвечивание
работает одинаково на любой исходной яркости.

Снег и туман легли на тот же механизм даром: снег — вторая форма тех же
частиц, туман — только числа в таблице окружения (470 → 207 м), осадков у него
нет. Туман при этом **дешевле ясного дня**, потому что поджимает отсечение.
Снежного покрытия в `trackmesh.js` нет: полотно под снегом остаётся сухим,
неизвестное значение падает на `clear`.

#### Смена погоды по ходу гонки: намеренно не сделана

`renderer.setEnvironment` при смене погоды делает `disposeRace()` +
`createRace()`, потому что небо, туман, свет и мокрое полотно **запечены в
геометрию и вершинные цвета**. Пересборка — 8–18 мс по 12.14 плюс машины,
тени, конусы фар, боксы и кубкарта отражений, и она сбрасывает `camReady`:
посреди заезда это провал кадра и прыжок камеры у всех разом. Дешёвая
половинка (включить только меш осадков) выглядит сломанной — дождь идёт,
полотно сухое. Чтобы стало дёшево, надо снять «мокрость» с запекания в uniform
шейдера полотна и научить небо, туман и свет интерполироваться без пересборки.
Это отдельная работа, и она больше, чем вся эта задача.

#### Враждебные входы

24 из 24 отбиты кодом `bad_weather` с текстом «погода: ожидается одно из
clear, wet, snow, fog»: мусорная строка, число, дробь, `null`, объект, список,
булево, `WET`, пустая строка, `wet ` с пробелом, **кириллическая подделка
`wеt`**, строка на 5000 символов — каждое по обоим путям, `create_room` и
`update_settings`. Соединение после всего живо, отсутствие поля сохраняет
прежнее значение.

### 12.20. Этап 2: траффик и происшествия на дороге

Две настройки комнаты: `traffic: off | sparse | dense`, `events: off | rare |
often`. Умолчание у обеих — `off`, поэтому комната без явного выбора ведёт
себя ровно как до этой работы. Проверка в `room.py` таблицей `ROAD_FIELDS`,
коды ошибок `bad_traffic` / `bad_events`.

#### Траффик едет в координатах ТРАССЫ, а не мира

Это главное решение участка. Запись гонщика (27 байт) везёт круг, место,
заряд заноса, угол руля и вектор скорости в мировых координатах — болванке
это не нужно и не будет нужно. Болванка по построению держится трассы,
поэтому её положение описывается дугой и смещением от оси: `u8 ident`
(номер в пуле плюс вид), `u16 s_q` (дуга, 3–5 см), `i8 lat_q` (0,1 м),
`i8 dyaw_q` (курс минус курс касательной, 1,4°), `u8 spd_q` (0,25 м/с).

**Шесть байт против двадцати семи — и при этом точнее.** Клиент
восстанавливает точку по той же осевой линии, по которой её считал сервер,
поэтому квантование не сносит болванку с полотна. `MAX_CARS = 8` не тронут:
гонщики и траффик — разные массивы.

Потолки: `MAX_TRAFFIC = 12`, `TRAFFIC_LOOKS = 12`, `MAX_ROAD_EVENTS = 6` —
оба идентификатора влезают в половину байта.

Байты при 20 Гц: 290 без траффика (5,8 КБ/с), 339–363 при плотном,
412 с шестью происшествиями (8,2 КБ/с). В живой гонке на `avenue` средний
пакет 252 → 336 байт, рост 34 %, максимум 396 при потолке 414.

Тик: 0,063 мс без траффика, 0,211 мс при двенадцати болванках и частых ДТП —
**11 % бюджета в 2 мс**. Одна болванка стоит 10,5 мкс. Выключенный траффик
стоит два `if` и в замере неотличим от прежних значений.

#### Отрисовка: два вызова на весь поток

Болванке собирается ОДНА слитая геометрия (кузов, четыре колеса, фары,
стопы) через тот же `buildCarMesh`, что и гонщику, и все болванки одного
силуэта рисуются одним `InstancedMesh` с инстансным цветом. Силуэтов два,
значит потолок — **два вызова на любое число болванок**; наивно было бы 48.
Происшествия — ещё два. Тени, маяки и перевёрнутые машины идут в уже
существующие меши и стоят ноль. Пик в живом прогоне 33 вызова при 37 тыс.
треугольников, запас до 50 остался.

Плата за один вызов: **колёса у болванок не крутятся**.

#### Честность закрыта построением, а не подкруткой

1. **Появлений по ходу гонки нет вообще.** Болванки расставляются один раз
   до старта и просто едут — «выскочить перед носом» физически нечем.
2. Перед решёткой держится чистый коридор 190 м.
3. Полоса пересчитывается каждый тик по ФАКТИЧЕСКОЙ полуширине: на
   `serpentine` полотно сужается с 6,25 до 3,75 м, и полоса, выбранная на
   широком участке, уводила болванку на газон.
4. Адаптивный круиз: борт о борт две болванки не встают, стены поперёк
   трассы не образуется.
5. Застрявшая сдаёт назад, а если безнадёжно — переставляется, но только
   туда, где до неё всем гонщикам не ближе 260 м.

Происшествия предсказуемы двумя независимыми механизмами: фаза
предупреждения 3 с (маяки и разметка уже видны, физики ещё нет) и выбор
места так, что ни один гонщик не ближе `max(75 м, v × 4,5 с)`, а участок
перед ним обязан просматриваться — суммарный поворот осевой на 55 м меньше
0,52 рад, с отдельной проверкой середины, иначе S-образный кусок прошёл бы
с нулевой разницей на концах.

**Физика происшествий не трогает ни `physics.py`, ни `physics.js`.** Масло и
обломки подменяют характеристики ДО шага (личная копия `CarStats`), твёрдое
препятствие выталкивает ПОСЛЕ — как стена трассы из шага 14. Порядок
операций 6.2 внутри шага дословно прежний. Та же категория, что
`resolve_collisions`.

#### Урок про шаткую проверку (дополнение к 12.17)

Проверка «рядом с болванкой остаётся проезд» с порогом 4,0 м падала в двух
прогонах из трёх: 3,9 / 3,9 / 4,3. Разбор дал два вывода, оба стоит помнить.

**Первый: недетерминированность пришла из чужого генератора.** `new_sim`
засевает `sim.items.rng`, а проверки звали `Simulation(...)` напрямую — там
оставался общий генератор модуля. Выпадение бонусов меняло поведение ботов,
боты по-разному толкали болванок, геометрия плыла. Лечится `_road_sim(...)`,
который засевает `items.rng`, `traffic.rng` и `road.rng` от одного зерна.

**Второй: мгновенный выброс — не то, что надо мерить.** Просветов ниже 4,0 м
на `serpentine` за две минуты оказалось восемь тиков из ~65 000, самая
длинная просадка — четыре тика, 67 мс. Причина не та, что предполагалась:
в момент худшего замера болванка проходила через осевую линию **после
толчка гонщика**, а не плелась за уезжающей целью. Гарантия `_lane_at` при
этом цела, отстаёт слежение за ней.

Поэтому проверка меряет теперь **устойчивый** просвет — лучший за скользящие
полсекунды. Пороги выведены из габарита машины (1,90 м), а не из того, что
проходит: устойчивый **4,6 м** = 2,4 ширины (замерено 4,79), мгновенный
**2,85 м** = полторы ширины (замерено 3,84), плюс отдельная проверка, что
узкий просвет не держится дольше секунды (замерено 0,22 с).

**Правило: порог, подобранный так, чтобы прогон проходил, — это не проверка.
Порог обязан выводиться из физической величины, и рядом с ним должен лежать
замеренный запас.**

#### Чего в участке нет — честный список

* JSON-события `race_event` для происшествий не шлются: всё едет снапшотом.
  Цена — у HUD и звука нет крюка «сейчас рванёт», предупреждение только
  визуальное.
* Колёса у болванок не крутятся.
* Бита «в полёте» в снапшоте нет — все восемь бит флагов заняты, рендер
  выводит его из высоты.
* Столкновения с болванками и препятствиями клиент не предсказывает — как и
  столкновения машина-машина, которые контракт уже так оставил. Масло и
  обломки предсказывает, там расхождения нет.
* Мигание маяков идёт по местным часам, у двух игроков фазы разные.

### 12.21. Этап 4a: сетка полотна внутри модуля и генерация раскладок ABI

Подготовка к смене физики на Rapier. Физика на этом этапе **не менялась**:
игра по-прежнему целиком на арифметике раздела 6, файлы `game/`, `server/`
и `static/` не тронуты. Проверено лично: сверка сеток совпала на всех пяти
трассах, импортов в модуле ноль, md5 сходится, генератор сверяет себя.

#### Сетку строит модуль, а не хозяин

Раньше хозяин строил треугольную сетку и заливал её готовой. **Это
возвращало ровно ту болезнь, ради лечения которой затеян весь этап:** сетку
пришлось бы строить и в `game/track.py`, и в `static/js/track.js`, и они
обязаны были бы совпасть до бита — вместо двух физик, обязанных совпасть,
получились бы две геометрии, обязанные совпасть.

Теперь хозяин заливает **квантованную осевую линию** — те же девять массивов
из 12.1, — а модуль сам разворачивает её в вершины и треугольники. Старые
экспорты `rp_track_alloc_verts` / `rp_track_alloc_tris` / `rp_track_commit`
убраны намеренно, а не оставлены «на всякий случай»: держать обе дороги
значит держать открытой ту самую дверь.

Следствие для 12.1: те же девять массивов теперь **не картинка, а вход
физики**. Квантование через `_f32()` из 7.2 становится несущей частью
физического контракта, а не приёмом ради компактного JSON.

| трасса | точек | треуг. | заливка было | стало | сборка |
|---|---:|---:|---:|---:|---:|
| avenue | 1327 | 15 924 | 295,5 КБ | **46,7 КБ** | 13,9 мс |
| ridge | 1208 | 14 496 | 269,0 | 42,5 | 11,5 мс |
| serpentine | 774 | 9 288 | 172,3 | 27,2 | 7,1 мс |
| industrial | 692 | 8 304 | 154,1 | 24,3 | 6,0 мс |
| office | 687 | 8 244 | 153,0 | 24,2 | 5,9 мс |
| **всего** | | | **1043,8 КБ** | **164,8 КБ** | в 6,3 раза меньше |

Поперечный разрез — семь столбцов: верх и низ левой стены, левая кромка,
ось, правая кромка, низ и верх правой стены. Счёт: **nv = 7N, nt = 12N**.
`WALL_MARGIN` и `WALL_HEIGHT` приходят в `rp_track_build` снаружи — модуль
игровых констант не знает. Отсюда новая константа контракта:
**`WALL_HEIGHT = 2.0`**. Раньше это число жило только в скрипте разведки, а
от него зависит сетка, и оба хозяина обязаны передать одно и то же.
`WALL_MARGIN = 2.5` из 12.7 теперь тоже геометрия полотна, а не только зона
вылета.

#### Правило про f64-промежуток

**Промежуточные выражения вершины (`x + nx*lateral`) считаются в f64 и
опускаются в f32 один раз, на записи.** Если написать очевидный цикл целиком
в f32, **2,43 % координат (1593 из 65 632) разъезжаются на единицу
последнего разряда** — по трассам от 1,25 % на `ridge` до 6,36 % на `office`.

Согласие сервера с клиентом это не сломало бы (оба гоняют один `.wasm`), но
сетка тихо уехала бы от нынешней геометрии и от аналитической границы, по
которой `track.py` и `track.js` считают прогресс и выталкивание. f64-промежуток
даёт ровно то, что посчитал бы любой хозяин: у Python и JS числа как раз f64,
а у wasm нет ни слитого умножения-сложения, ни расширенных регистров —
результат один на всех движках.

Записано отдельным правилом, потому что следующий человек «упростит» это до
f32 и тихо сдвинет геометрию.

#### Раскладки ABI генерируются

Руками правится **только** `tools/abi_layout.json` (7 структур, 100 полей,
4 константы, 6 общих буферов). `python3 tools/gen_abi.py` выпускает:

* `native/src/abi_gen.rs` — `#[repr(C)]` структуры плюс проверки `offset_of!`
  на каждое поле, то есть сломанная раскладка валит **сборку**, а не отладку;
* `native/abi/abi_layout.py` и `native/abi/abi_layout.js` — индексы полей для
  сервера и браузера.

`python3 tools/gen_abi.py --check` сверяет лежащее в репозитории с выводом и
возвращает 1 при расхождении. **Эту команду надо завести в общий прогон
проверок на 4b** — сейчас она не вызывается ниоткуда.

На 4b выпущенные раскладки **импортируются** из `game/` и `static/js/`, а не
переписываются смещениями руками. Иначе вместо двух физик получатся три
описания одной структуры — та же болезнь с другой стороны.

#### ЗАКРЫТО: туннелирование сквозь полотно было артефактом замера

**Этот пункт был записан как открытый риск по итогам 4a и оказался ошибкой
измерения. Разобрано на 4c, здесь оставлено целиком — как урок, а не как
риск.**

Замер 4a говорил: на 60 м/с машина проваливается сквозь асфальт, дыра
зависит от места падения, лечится только CCD. Ни одно из трёх утверждений
не подтвердилось.

Причина найдена и воспроизведена: стенд ронял **пачку из 16 машин в
0,5–1,0 м друг от друга** при ширине кузова 1,56–2,02 м. Кузова
пересекались ещё в воздухе, солвер расталкивал их — и расталкивал сквозь
полотно. **72 % «провалов» с 200 м исчезают полностью, стоит развести
машины по длине трассы.** Отсюда же и загадочная зависимость от места
падения: она была зависимостью от того, с кем машина оказалась в одной
пачке.

Честное покрытие после разноса:

| проверка | точек | провалов |
|---|---:|---:|
| avenue, падение 200 м | 4750 | **0** |
| пять трасс, 200 м и 800 м, в пределах полотна | 8536 | **0** |
| езда 8 машин × 6000 тиков × 5 трасс на 50–52 м/с с трамплинами | 240 000 машино-тиков | **0** |

Единственные оставшиеся провалы — падение с 800 м в точку дальше 9,25 м от
оси, где полотно вместе с обочиной кончается в 8,39 м: машина падает **мимо
сетки**, а не сквозь неё. Никакой CCD этого не меняет и не должен.

Цена обоих лечений всё равно измерена (avenue, 8 машин, 50 м/с, 5000 тиков):

| | среднее | p99 | множитель |
|---|---:|---:|---:|
| как есть | **165,4 мкс** | 276,3 | — |
| жёсткий CCD на кузове | 1360,3 мкс | 1946,1 | **×8,2** |
| мягкий CCD, `soft_ccd_prediction(2.0)` | 232,2 мкс | 391,3 | ×1,40 |

**Решение: не ставить ни то, ни другое.** Жёсткий CCD не проходит по
бюджету сам по себе — 1,36 мс при бюджете 2 мс, и это только мир Rapier, до
всего остального тика; на N5105 это 1,5–2,0 мс. Мягкий по цене прошёл бы, но
**меняет хэш мира**, то есть обнуляет все числа сверки 4b и все числа
ощущения. Платить перестройкой физики за дыру, которой нет, нельзя. Мягкий
CCD остаётся заготовкой: это одна строка в `RigidBodyBuilder` в `spawn_car`,
цена известна, и пункт стоит перемерить на 4e, когда появятся настоящие
столкновения и приземления с трамплинов.

**Урок, ради которого это оставлено в контракте.** Замер, сделанный один
раз и не перепроверенный, попал в контракт как факт и чуть не стоил этапу
восьмикратной цены тика. Прежде чем записывать измеренную аномалию в
известные риски, надо проверить сам стенд: не создаёт ли он то, что меряет.
Это ровно та же ошибка, что в 12.17 (ложный красный от нагрузки) и в 12.20
(шаткий порог), только в третьем обличье.

### 12.22. Этап 4b: wasmtime в репозитории и хозяин модуля на обеих сторонах

Проверено лично: вендорный wasmtime грузится в изолированном интерпретаторе
(`python3 -I` с пустым окружением) при полном отсутствии системного пакета;
`tools/test_sim.py` — 154 из 154 при загрузке 0,10; `tools/smoke_test.py` —
34 из 34 при умолчальном флаге.

#### Зависимости: уточнение к разделу 1

tornado **не лежит** в репозитории — он установлен на машинах заказчика.
wasmtime там нет, поэтому он лежит папкой `vendor/`: 42 файла, 30,4 МБ, из
которых 29,8 МБ — `_libwasmtime.so`. В git-объектах это около **9,3 МБ**
(zlib сжимает библиотеку).

`tools/vendor_wasmtime.py --wheel <файл>` распаковывает колесо
воспроизводимо: фиксированные права и mtime, порядок по имени, две
распаковки подряд дают побайтово одинаковый `vendor/wasmtime.lock.json`.
SHA-256 колеса закреплён в скрипте, чужое принимается только с `--pin`.
`--check` сверяет 42 файла по SHA-256 и правам, не имея колеса под рукой.

Обе сторожевые проверки — `gen_abi.py --check` и `vendor_wasmtime.py --check` —
заведены **первыми** в `tools/test_sim.py` (`check_generated`). Первыми
потому, что при разъехавшейся раскладке все остальные числа считаны по
неверным смещениям. Это закрывает пункт, оставленный открытым в 12.21.

#### Флаг `RACING_PHYSICS` / `run.py --physics`

Два значения: **`classic`** (умолчание) и **`shadow`**.

Полноценного «Rapier считает гонку» на 4b **намеренно нет**. Подмена шага
требует переноса прогресса, столкновений, выталкивания и бонусов — это 4c и
4e, — а сделанная наполовину, она и была бы тем самым «переключили и
молимся», который запрещён. В `shadow` мир Rapier крутится **рядом** с
гонкой на тех же вводах и в том же темпе, состояние машин из него не
берётся: это живой стенд для замеров и сверки, и поднятый флаг физически не
может испортить заезд.

Цена при выключенном флаге — **ноль в горячем пути**: выбор делается один раз
в `Simulation.__init__`, `attach()` подменяет `_step_cars` на экземпляре. Ни
одной новой проверки за тик. `game/physics.py` и `static/js/physics.js` не
тронуты ни строкой. При выключенном флаге `wasmtime` не попадает в
`sys.modules` вовсе, а маршрут `/native/...` отдаёт 404 — сервер снаружи
ровно такой же, как до 4b.

#### Один `.wasm` — один результат в четырёх движках

10 000 шагов, avenue, 8 машин, полотно из квантованной осевой 12.1. Сетка:
`verts=2619f2580a7d6d1c`, `tris=e966af9edc20bd80`. Хэш мира на тике 10 000 —
`d3e9970c09414d43`, состояния — `a4d972fec4f54c78`.

**Совпало во всех четырёх: wasmtime 48, Node 22 (V8), Chromium 141,
Firefox 142**, на всех семи контрольных точках. В управлении стенда нет ни
одной трансцендентной функции, поэтому одинаковость входов тут по
построению, а не на веру.

#### Цена в тике

| | среднее | p99 |
|---|---|---|
| полный тик, флаг выключен | 0,0677 мс | 0,1065 мс |
| полный тик, флаг `shadow` | 0,2584 мс | 0,4077 мс |
| мир Rapier, 8 машин | **171,1 мкс** | 284,9 мкс |
| то же, машины реально едут 50 м/с | 185,2 мкс | 385,7 мкс |

#### Открытый пункт: Firefox медленнее V8 в десять раз

Подтверждено на свежем Firefox 142, те же 8 машин: **Chromium 129 мкс/тик,

Клиент предсказывает одну машину, то есть около 165 мкс на кадр в Firefox —

что браузер непринципиален.

#### Две константы, живущие по копии

`WALL_MARGIN` импортируется (сервер — из `game/track.py`, клиент — из
`static/js/track.js`). А `WALL_HEIGHT = 2.0` и новое **`TRACK_FRICTION = 1.1`**
лежат по копии в каждом хозяине: в `abi_layout.json` их класть нельзя, это
поменяло бы `abi_gen.rs` и, значит, md5 модуля. **Менять только парой.** На
4c их правильно передавать клиенту в `race_init` рядом с трассой — тогда
копия исчезнет.

#### Дополнение к 12.1

У 4a записано, что девять массивов осевой — вход физики на сервере. Теперь то
же верно и для клиента: `Track.fromServer` кладёт `round(v, 3)` в
`Float32Array`, сервер держит `_f32(round(v, 3))` — одни и те же биты. На
этом держится совпадение хэшей мира, а не только компактность JSON.
